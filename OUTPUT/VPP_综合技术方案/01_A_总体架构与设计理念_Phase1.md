## 1. 核心设计理念

### 1.1 从"监测系统"到"头寸管理系统"

本方案的核心设计理念是将传统的"电力监测系统"重构为基于风险控制的**头寸管理系统**。这一范式转换体现在以下三个层面：

| 传统监测系统           | 金融级头寸管理系统                     |
| ---------------------- | -------------------------------------- |
| 被动监测电压/电流/功率 | 主动管理电力头寸（Position）           |
| 固定阈值告警           | 动态风险价值（VaR/CVaR）计算           |
| 事后分析报表           | 事前报价优化与事中风险对冲             |
| 单一站点独立运行       | 多站点聚合套利与风险分散               |
| 确定性控制逻辑         | 概率性报价策略（Price-Quantity Curve） |

**核心目标**：在动态电价下具备金融级的获利与避险能力。

### 1.2 三大设计原则

**原则一：数据流与控制流分离**

系统严格分离数据平面（Data Plane）和控制平面（Control Plane），确保控制指令的确定性延迟不受数据上报流量的影响。

**原则二：边端自治与云端协同**

边端具备完整的离线自治能力（≥72小时），云端负责全局优化和长期策略。边端在断网时根据最后一帧有效指令安全运行，网络恢复后自动同步。

**原则三：物理约束优先于经济优化**

所有调度决策必须在物理约束引擎的硬性边界内执行。热容量、I²t、电压质量、三相平衡等物理约束的优先级高于任何经济优化目标。

### 1.3 Phase 1 设计原则（10万级）

在三大设计原则基础上，Phase 1 增加以下专项原则：

| 原则               | 说明                                                   |
| ------------------ | ------------------------------------------------------ |
| **最小可行闭环**   | 先跑通"聚合→报价→调度→结算"全链路，再优化              |
| **单资源类型起步** | 以工商业储能为主攻，充电桩辅助，暂不涉及光伏/空调/HEMS |
| **集中式优化**     | 资产数<10K时无需ADMM分布式求解，集中式Pyomo+CBC即可    |
| **安全适度**       | 三区架构（I/II/III），暂不需要DMZ区和IV区              |
| **兼容优先**       | 所有数据模型、接口标准、组件选型与千万级方案保持一致   |

### 1.4 四川特性设计考量

本方案针对四川省的特殊环境进行了专项设计：

| 四川特性           | 技术影响                                         | 方案应对                              |
| ------------------ | ------------------------------------------------ | ------------------------------------- |
| 丰枯水期差异电价   | 电价模型需区分丰水期（6-10月）和枯水期（11-5月） | 多版本分时电价元数据 + 季节性电价系数 |
| 陇电入川特高压直流 | 跨省联络线容量影响调度决策                       | 联络线ATC建模 + Pyomo约束（Phase 2+） |
| 尖峰时段动态调整   | 尖峰时段随天气/负荷动态变化                      | 动态电价响应引擎 + 日前预测           |
| 基本电费消减       | 需量管理直接影响业主成本                         | 需量管理策略 + 滚动15分钟需量控制     |
| 四川保供电预警     | 极端天气下需切换保供模式                         | 应急接管模式（Phase 2+）              |

> **Phase 1 与千万级方案的关键差异**：
>
> - 优化架构：集中式Pyomo+CBC（非ADMM+Gurobi）
> - 安全架构：三区（I/II/III），无DMZ/IV区
> - DR通道：单通道OpenADR（非双通道）
> - 结算：仅日前现货（非全市场多品种）
> - 边端：STM32单机+外部看门狗（非双冗余）
> - 时序库：TimescaleDB单机（非TDengine集群）
> - 消息中间件：RabbitMQ单节点（非RabbitMQ+Kafka桥接）
> - NILM感知：暂不部署（仅计量层）
> - HEMS：暂不部署（聚焦工商业场景）

### 3.4 Phase 1 安全架构（三区 + 硬件反向隔离装置）

### 3.5 Phase 1 开源选型

> **⚠️ 求解职责切分约束**：云端Pyomo+CBC**仅求解到站点/台区级别**（100~500个变量），为每个站点下发总功率目标（P_target）。站内充电桩的DLB动态负载均衡算法**强制下沉**到边端OpenEMS中通过硬编码规则本地消化。此约束确保CBC求解器永远控制在≤500个节点以内，单轮求解时间<3秒。若将DLB约束纳入云端模型，约束矩阵将暴涨至数万维，CBC极易发散不收敛。

### 4.2 远期海量资产优化架构：双层求解与ADMM

> **背景**：当聚合的站点、台区和充电桩数量达到千万级时，集中式求解的数学规划矩阵构建时间和求解器计算时间会随资产数量呈指数级增长。远期采用双层优化+ADMM分布式求解架构。

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  上层：交易层（经济优化）                                                     │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │  Pyomo 求解器（Gurobi）                                                │  │
│  │  输入：虚拟大节点聚合参数（总SOC、总可调容量、总功率上下限）              │  │
│  │  输出：虚拟大节点功率分配目标（P_target_cluster）                        │  │
│  │  约束：联络线ATC、市场出清价、辅助服务报价、CVaR风险限额                 │  │
│  │  规模：≤10K 虚拟节点（而非 10M 物理资产）                               │  │
│  └───────────────────────────────────────────────────────────────────────┘  │
│                                    │ ADMM 协调层                            │
│                                    │ ρ 参数动态调优                         │
│                                    │ 残差监控与收敛判定                     │
│                                    ▼                                        │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │  下层：聚合层（物理约束）                                              │  │
│  │  FlexMeasures（下层求解器）+ OpenEMS（最下层执行器）                    │  │
│  │  输入：P_target_cluster（上层下发的功率分配目标）                        │  │
│  │  输出：各设备实际调度指令（P_actual_device）                             │  │
│  │  约束：三相平衡、变压器容量、SOC均衡、I²t热容量、电压质量                │  │
│  │  规模：每个自治域 ≤10K 物理资产                                         │  │
│  └───────────────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────────────┘
```

#### 6.3a 断网重连数据幂等性机制

> **背景**：工商业储能+充电桩在进行日前/日内交易时，高度依赖数据连续性。断网期间缺失的电表功率数据若补传时发生主键冲突或数据库过载，将导致日前偏差结算错误。

**数据补传幂等性（Upsert）**：

```sql
-- ThingsBoard Gateway 补传逻辑
INSERT INTO ts_data (time, device_id, value)
VALUES ($1, $2, $3)
ON CONFLICT (time, device_id)
DO UPDATE SET value = EXCLUDED.value, updated_at = NOW();
```

**Gateway 限流配置**：

```yaml
# Gateway 配置参数
history_replay:
  rate_limit: 100 # 每秒最高100条历史记录
  window_seconds: 5 # 滑动窗口5秒
  max_queue_size: 10000 # 最大排队数，超过则丢弃旧数据
  retry_interval: 30 # 重试间隔30秒
```

**测试验证**（对应 §9.3 断网重连测试用例）：

- 验证 `ON CONFLICT` upsert 幂等性：重复补传同一时间戳数据不报错
- 验证 100条/s 限流：Gateway 端滑动窗口限流生效，TimescaleDB CPU 不超 80%
- 验证数据完整性：断网2小时后重连，补传数据与原始数据完全一致
