## 1. 核心设计理念

### 1.1 从"监测系统"到"头寸管理系统"

本方案的核心设计理念是将传统的"电力监测系统"重构为基于风险控制的**头寸管理系统**。这一范式转换体现在以下三个层面：

| 传统监测系统           | 金融级头寸管理系统                     |
| ---------------------- | -------------------------------------- |
| 被动监测电压/电流/功率 | 主动管理电力头寸（Position）           |
| 固定阈值告警           | 动态风险价值（VaR/CVaR）计算           |
| 事后分析报表           | 事前报价优化与事中风险对冲             |
| 单一站点独立运行       | 多站点聚合套利与风险分散               |
| 确定性控制逻辑         | 概率性报价策略（Price-Quantity Curve） |

**核心目标**：在动态电价下具备金融级的获利与避险能力。

### 1.2 三大设计原则

**原则一：数据流与控制流分离**

系统严格分离数据平面（Data Plane）和控制平面（Control Plane），确保控制指令的确定性延迟不受数据上报流量的影响。

**原则二：边缘自治与云端协同**

边缘端具备完整的离线自治能力（≥72小时），云端负责全局优化和长期策略。边缘端在断网时根据最后一帧有效指令安全运行，网络恢复后自动同步。

**原则三：物理约束优先于经济优化**

所有调度决策必须在物理约束引擎的硬性边界内执行。热容量、I²t、电压质量、三相平衡等物理约束的优先级高于任何经济优化目标。

### 1.3 四川特性设计考量

本方案针对四川省的特殊环境进行了专项设计：

| 四川特性           | 技术影响                                         | 方案应对                              |
| ------------------ | ------------------------------------------------ | ------------------------------------- |
| 丰枯水期差异电价   | 电价模型需区分丰水期（6-10月）和枯水期（11-5月） | 多版本分时电价元数据 + 季节性电价系数 |
| 陇电入川特高压直流 | 跨省联络线容量影响调度决策                       | 联络线ATC建模 + Pyomo约束             |
| 尖峰时段动态调整   | 尖峰时段随天气/负荷动态变化                      | 动态电价响应引擎 + 日前预测           |
| 基本电费消减       | 需量管理直接影响业主成本                         | 需量管理策略 + 滚动15分钟需量控制     |
| 四川保供电预警     | 极端天气下需切换保供模式                         | 应急接管模式 + 联络线闭锁风险模拟     |

### 2.3 GB/T 38755-2020 虚拟电厂技术导则合规映射

GB/T 38755-2020 要求虚拟电厂系统包含以下核心功能模块，本架构的对应实现如下：

| GB/T 38755 要求 | 本架构对应模块               | 实现方式                                                                                |
| --------------- | ---------------------------- | --------------------------------------------------------------------------------------- |
| 资源聚合层      | 聚合层 - 资源聚合调度        | FlexMeasures + 自研聚合引擎[^附录A]                                                     |
| 运营管理层      | 聚合层 - 智能台区/充电桩/EMC | 自研 + OCPP + ThingsBoard Server (规则引擎/可视化) + ThingsBoard Gateway (边缘数据采集) |
| 交易层          | 交易层 - 报价引擎/合同引擎   | epftoolbox[^附录B] + Pyomo + 自研                                                       |
| 功率预测        | 功率预测服务（独立模块）     | 详见2.4节                                                                               |
| 调节能力评估    | 调节能力评估模块（独立模块） | 详见2.5节                                                                               |
| 市场申报        | 报价引擎 - 市场接口          | REST API + 文件交换                                                                     |
| 调度响应        | 聚合调度 - 指令下发          | MQTT/WebSocket                                                                          |
| 计量结算        | 结算层 - 智能结算与清算      | PostgreSQL NUMERIC                                                                      |
| 安全防护        | 安全架构 - 等保2.0三级       | 详见第10章                                                                              |

> **⚠️ 关于 FlexMeasures 与 Pyomo 的关系**：FlexMeasures 内部已集成 Pyomo 作为其调度引擎的底层求解器。文档中将两者分开标注，是因为它们解决不同层面的优化问题——FlexMeasures 用于聚合层的**资源调度优化**（物理约束下的功率分配），Pyomo 独立用于交易层的**市场报价优化**（经济约束下的报价策略）。两者在联络线潮流建模等场景中可协同使用（见 §6.2）。

### 2.4 功率预测服务模块（新增）

根据GB/T 38755要求，增加独立的功率预测服务模块，包含光伏预测、负荷预测、风电预测，通过预测融合引擎输出给报价引擎、聚合调度和风险管控。详见后续章节。

### 2.5 调节能力评估模块（新增）

根据GB/T 38755要求，增加调节能力评估模块，评估VPP聚合资源的上下可调容量、响应速率、调节精度，支持电池、光伏、充电桩、空调、热水器等多种资源类型。详见后续章节。

### 3.3 各层职责与交互

| 层级       | 核心职责                               | 部署位置             | 响应时间    | 通信协议                                               |
| ---------- | -------------------------------------- | -------------------- | ----------- | ------------------------------------------------------ |
| **边缘层** | 设备接入、本地控制、NILM感知、离线自治 | 家庭/台区/充电站现场 | ≤1秒        | Modbus/OCPP/MQTT/IEC 61850/IEC 60870-5-104/IEEE 2030.5 |
| **聚合层** | 资源聚合、台区管理、充电网络、EMC管理  | 区域数据中心         | 秒~分钟级   | JSON-RPC/WebSocket/OpenADR 2.0                         |
| **交易层** | 报价优化、价格预测、交易策略           | 云端/中心机房        | 分钟~小时级 | REST API/消息队列                                      |
| **结算层** | 多市场结算、偏差考核、收益分配         | 云端                 | 日级        | 文件交换/API                                           |

> **⚠️ 关于跨层级组件的说明**：本架构中部分组件同时出现在多个层级，但用途和部署方式不同，特此说明：
>
> - **消息中间件（RabbitMQ / Kafka）**：边缘层使用 RabbitMQ（轻量级，适合资源受限的边缘网关），聚合层和交易层使用 Kafka（高吞吐量，适合云端海量消息处理）。两者通过桥接器连接，实现边缘→云端的消息透传。
> - **时序数据库（TimescaleDB / TDengine / InfluxDB）**：边缘层部署轻量级实例用于本地缓存（断网时暂存数据），聚合层部署集群用于全量时序数据存储和分析。TimescaleDB 为推荐选型（BSD 许可证，零许可成本，完全兼容 PostgreSQL 生态），TDengine 为国产化备选（AGPL 许可证，需商业许可）。
> - **PostgreSQL**：聚合层用于业务数据存储（合同、设备信息、用户数据），结算层用于财务数据存储（账单、结算记录、交易流水）。结算层强制使用 NUMERIC 类型确保财务精度。
> - **ThingsBoard**：ThingsBoard Server 部署在聚合层，提供规则引擎、可视化、设备管理能力；ThingsBoard Gateway 部署在边缘层，负责协议转换和数据采集转发。两者通过 MQTT/TLS 加密通信。
> - **Pyomo 与 FlexMeasures**：详见 §2.3 和 §7.1 的注释说明。

### 3.4 海量资产优化架构：双层求解与 ADMM（新增）

> **⚠️ 风险背景**：当聚合的站点、台区和充电桩数量达到千万级时，将全省所有资产塞进一个 Pyomo 模型进行集中式求解，数学规划矩阵的构建时间和求解器（CBC/Gurobi）的计算时间会随资产数量呈指数级增长，可能打破交易层"分钟级决策"的时效要求。

#### 3.4.1 双层优化架构总览

本方案采用**双层优化（Bi-level Optimization）+ ADMM（交替方向乘子法）** 分布式求解架构，将海量资产优化拆解为上下两层：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  上层：交易层（经济优化）                                                     │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │  Pyomo 求解器（CBC/Gurobi）                                            │  │
│  │  输入：虚拟大节点聚合参数（总SOC、总可调容量、总功率上下限）              │  │
│  │  输出：虚拟大节点功率分配目标（P_target_cluster）                        │  │
│  │  约束：联络线ATC、市场出清价、辅助服务报价、CVaR风险限额                 │  │
│  │  规模：≤10K 虚拟节点（而非 10M 物理资产）                               │  │
│  └───────────────────────────────────────────────────────────────────────┘  │
│                                    │ ADMM 协调层                            │
│                                    │ ρ 参数动态调优                         │
│                                    │ 残差监控与收敛判定                     │
│                                    ▼                                        │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │  下层：聚合/边缘层（物理约束）                                          │  │
│  │  FlexMeasures / OpenEMS 本地求解器                                      │  │
│  │  输入：P_target_cluster（上层下发的功率分配目标）                        │  │
│  │  输出：各设备实际调度指令（P_actual_device）                             │  │
│  │  约束：三相平衡、变压器容量、SOC均衡、I²t热容量、电压质量                │  │
│  │  规模：每个自治域 ≤10K 物理资产                                         │  │
│  └───────────────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────────────┘
```

#### 3.4.2 上层：交易层虚拟节点聚合

将物理资产按"供电分区 + 资源类型"聚合为虚拟大节点（Cluster），每个 Cluster 对外暴露以下聚合参数：

| 聚合参数       | 说明                                 | 计算方式                            |
| -------------- | ------------------------------------ | ----------------------------------- |
| **总可调容量** | Cluster 内所有资源的上下可调范围之和 | Σ(P_max_i - P_min_i)                |
| **总 SOC**     | 储能资源的加权平均 SOC               | Σ(SOC_i × E_rated_i) / Σ(E_rated_i) |
| **总功率基线** | Cluster 的基准运行功率               | Σ(P_base_i)                         |
| **响应速率**   | Cluster 整体功率变化率上限           | min(ramp_rate_i)                    |
| **调节精度**   | Cluster 整体功率控制精度             | max(precision_i)                    |

**聚合粒度建议**：

| 场景             | 聚合粒度              | 虚拟节点数（全省） |
| ---------------- | --------------------- | ------------------ |
| Phase 1 单站     | 按设备类型聚合        | ≤10                |
| Phase 2 区域聚合 | 按台区 + 资源类型     | ≤1,000             |
| Phase 3 全省规模 | 按供电分区 + 资源类型 | ≤10,000            |

#### 3.4.3 下层：边缘/聚合层本地求解

每个自治域（台区/充电站群）内的 FlexMeasures 或 OpenEMS 接收上层下发的 P_target_cluster，在本地消化物理约束：

| 物理约束       | 说明                         | 违反后果                 |
| -------------- | ---------------------------- | ------------------------ |
| **三相平衡**   | 各相功率偏差 ≤ 15%           | 变压器过热、保护动作     |
| **变压器容量** | 总视在功率 ≤ 额定容量 × 1.05 | 变压器寿命缩短、跳闸     |
| **SOC 均衡**   | 同站多台储能 SOC 偏差 ≤ 10%  | 部分电池过充/过放        |
| **I²t 热容量** | 电缆/断路器热积累 ≤ 额定值   | 绝缘老化、火灾风险       |
| **电压质量**   | 并网点电压偏差 ≤ ±7%         | 逆变器脱网、电能质量罚款 |

#### 3.4.4 ADMM 协调机制

上下层之间通过 ADMM 算法迭代收敛，实现分布式一致性：

```
目标：min Σ(f_upper(P_cluster) + f_lower(P_device))
约束：P_cluster = Σ(P_device)  // 一致性约束

ADMM 迭代步骤：
1. 上层求解：P_cluster^(k+1) = argmin( f_upper + (ρ/2) × ||P_cluster - Σ(P_device^(k)) + u^(k)||² )
2. 下层求解：P_device^(k+1) = argmin( f_lower + (ρ/2) × ||P_cluster^(k+1) - Σ(P_device) + u^(k)||² )
3. 对偶更新：u^(k+1) = u^(k) + (P_cluster^(k+1) - Σ(P_device^(k+1)))
4. 收敛判定：||P_cluster^(k+1) - Σ(P_device^(k+1))|| < ε
```

**收敛时间参考**：

| 场景规模           | 资产数         | 求解器           | 单轮求解时间 | 收敛轮次 | 总收敛时间  | 可行性            |
| ------------------ | -------------- | ---------------- | ------------ | -------- | ----------- | ----------------- |
| Phase 1 单站       | ≤100 资产      | CBC（开源）      | <0.5s        | 5-10     | **3-5s**    | ✅ 完全可行       |
| Phase 2 区域聚合   | ≤10K 虚拟节点  | Gurobi（商业）   | 1-2s         | 10-20    | **20-40s**  | ✅ 可行           |
| Phase 3 全省规模   | ≤100K 虚拟节点 | Gurobi（分布式） | 3-5s         | 15-30    | **60-150s** | ⚠️ 需商业许可     |
| 极端场景（不推荐） | >500K 节点     | -                | >10s         | >30      | >300s       | ❌ 建议拆分自治域 |

> **结论**：以 5 分钟（300s）交易窗口为基准，双层 ADMM 架构在省内大规模场景下预留 50% 安全余量（≤150s 完成收敛），完全满足分钟级决策时效要求。

#### 3.4.5 ρ 参数动态调优策略

ADMM 的惩罚参数 ρ 直接影响收敛速度：

| ρ 值     | 收敛特性                       | 适用场景                           |
| -------- | ------------------------------ | ---------------------------------- |
| ρ=0.5    | 收敛慢但稳定，不易震荡         | Phase 1 小规模调试                 |
| ρ=1.0    | 平衡收敛速度与稳定性           | **默认值，适用于大多数场景**       |
| ρ=2.0    | 收敛快但可能震荡               | Phase 3 大规模场景，需配合残差监控 |
| 动态调优 | 残差增大则 ρ×1.5，减小则 ρ×0.8 | **推荐方案**，自适应不同规模       |

#### 3.4.6 与现有架构的集成

| 现有组件                   | 在双层架构中的角色         | 修改要求                                              |
| -------------------------- | -------------------------- | ----------------------------------------------------- |
| **Pyomo（交易层）**        | 上层求解器，仅处理虚拟节点 | 需增加 Cluster 聚合接口，无需修改求解逻辑             |
| **FlexMeasures（聚合层）** | 下层求解器，处理物理约束   | 需增加 ADMM 客户端模块，接收 P_target 并返回 P_device |
| **OpenEMS（边缘层）**      | 最下层执行器，执行本地闭环 | 无需修改，仅需支持远程 P_target 设定                  |
| **ESB（胶水层）**          | ADMM 协调消息传递          | 需新增 ADMM 协调服务，管理 ρ 参数和收敛判定           |

## 4. 能源交换机范式

### 4.1 核心概念映射

本方案采用"能源交换机"（Energy Switch）作为核心架构范式，将EMS节点抽象为电力网络的智能交换节点：

| 交换机概念               | 电力系统映射       | 功能描述                                                   |
| ------------------------ | ------------------ | ---------------------------------------------------------- |
| **端口 (Port)**          | 设备接口           | 每个接入设备（充电桩、储能、逆变器、空调）视为一个逻辑端口 |
| **背板带宽 (Backplane)** | 台区额定功率       | 变压器容量决定节点的最大总吞吐量                           |
| **MAC地址表**            | 设备指纹库         | NILM识别的设备特征指纹，用于身份确认和物理身份校验         |
| **QoS优先级**            | 分级标签           | L1-L4分级决定带宽分配优先级                                |
| **路由表**               | 电力路由表         | 节点间拓扑关系和路由代价                                   |
| **流量整形**             | 斜率滤波           | 功率变化率控制，防止电压冲击                               |
| **拥塞控制**             | 协同减载           | 带宽不足时的有序减载机制                                   |
| **生成树协议(STP)**      | 潮流冲突预防与仲裁 | 防止多节点同时倒送电导致母线过载                           |
| **VLAN**                 | 供电分区隔离       | 不同供电分区的资源逻辑隔离                                 |
| **端口镜像**             | 数据镜像           | NILM监测数据的旁路采集                                     |

### 4.2 端口管理模型

每个接入设备在能量路由器中对应一个逻辑端口，端口状态机包含 DISCOVERY → ACTIVE → OFFLINE/DEGRADED/SHEDDING 等状态转换。

### 4.3 带宽分配模型

能量路由器采用加权公平队列（WFQ）算法进行带宽分配，按 L1-L4 分级标签分配权重，优先保障关键负荷带宽。

## 5. 数据流与控制流架构

### 5.1 三个闭环

系统数据流分为三个闭环，分别对应不同的时间尺度和控制目标：

| 闭环       | 时间尺度    | 关键路径延迟 | 说明                                      |
| ---------- | ----------- | ------------ | ----------------------------------------- |
| 实时控制环 | 毫秒级      | <200ms       | 传感器采样→物理约束校验→控制算法→指令下发 |
| 状态上报环 | 秒级        | <5s          | 设备状态→数据聚合→MQTT推送→云端存储→UI    |
| 交易决策环 | 分钟~小时级 | 15min~24h    | 市场数据→功率预测→报价优化→调度计划下发   |

> **⚠️ 关于三级响应架构（NILM → PCS 直连）**：针对电网频率/电压跌落的快速响应场景，本架构采用三级响应设计，确保安全性与实时性：
>
> | 响应级                | 时间尺度 | 控制路径                                         | 说明                                                                                                                                                                                                                       |
> | --------------------- | -------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
> | **第一级：硬件级**    | μs ~ ms  | STM32(NILM) ──[GPIO/PWM直连]──→ PCS              | STM32通过ADC以1kHz+采样电网电压/频率，检测到频率越限（<49.5Hz或>50.5Hz）或电压跌落时，通过硬件GPIO/PWM或高速SPI直接向PCS发送控制信号。**不经过任何软件协议栈**，确保确定性延迟。详见附录D[^附录D]关于STM32可靠性保障说明。 |
> | **第二级：边缘EMS级** | ms ~ s   | STM32 ──[CAN/SPI]──→ OpenEMS ──→ PCS(二次调整)   | STM32将检测数据通过内部总线上报本地OpenEMS，EMS运行本地控制闭环进行二次解算：确认硬件响应是否正确执行、评估是否需要进一步调整、记录SOE事件、执行本地安全逻辑。                                                             |
> | **第三级：云端级**    | s ~ min  | OpenEMS ──[MQTT]──→ ThingsBoard Gateway ──→ 云端 | OpenEMS将聚合后的状态上报云端，云端进行全局优化决策：更新报价策略、调整调度计划、记录事后分析。                                                                                                                            |
>
> **设计优势**：硬件级响应不受软件故障、网络中断、操作系统调度延迟的影响，关键路径延迟可控在<200ms。完全符合"数据流与控制流分离"原则（§1.2）和"边缘自治与云端协同"原则。

### 5.2 数据平面与控制平面分离

- **控制平面**：使用独立WebSocket连接（WSS协议），优先级最高，确定性延迟<10ms
- **数据平面**：使用MQTT协议（QoS 0/1/2），尽力而为传输，可压缩/批量传输
- 边缘端优先保障控制平面的带宽和CPU资源
- 云端崩溃时，控制平面降级为边缘自治模式，边缘端根据最后一帧有效指令继续运行

## 9. 胶水层架构设计

### 9.1 胶水层定位

胶水层（Glue Layer）是本架构中连接各开源组件的关键中间层，负责解决开源组件之间的集成缝隙。它不是独立部署的服务，而是一组集成逻辑的集合，分布在ESB（企业服务总线）和边缘网关中。

### 9.2 胶水层核心职责

| 职责             | 说明                                                   |
| ---------------- | ------------------------------------------------------ |
| **协议转换**     | 将Modbus/OCPP/61850等协议转换为统一内部消息格式        |
| **数据模型映射** | 将各开源组件的数据模型映射到统一的CIM兼容数据模型      |
| **状态同步**     | 确保边缘端和云端的状态一致性，处理断网重连后的数据同步 |
| **降级策略**     | 定义各组件失效时的降级行为，确保系统整体可用性         |
| **安全边界**     | 在各组件之间实施安全隔离，防止单点故障扩散             |
| **监控告警**     | 收集各组件的健康状态，触发告警和自动恢复               |

### 9.3 三级响应架构详解

> **⚠️ 本节是对 §5.1 中三级响应架构的详细展开说明。**

#### 9.3.1 第一级：硬件级响应（μs ~ ms）

**核心组件**：STM32 微控制器（NILM感知层）

**工作流程**：

- STM32 通过 ADC 以 1kHz+ 采样电网电压和频率
- 检测到频率越限（<49.5Hz 或 >50.5Hz）或电压跌落时，通过硬件 GPIO/PWM 或高速 SPI 直接向 PCS 发送控制信号
- **不经过任何软件协议栈**，确保确定性延迟
- 响应时间：μs ~ ms 级
- STM32 的可靠性保障措施及冗余机制选型详见附录D[^附录D]

**设计要点**：

- 使用独立供电轨，确保 STM32 不受 OpenEMS 主系统电源故障影响
- 外部硬件看门狗，独立于 MCU 时钟
- 双 Bank Flash，支持安全 OTA 和回滚

#### 9.3.2 第二级：边缘EMS级响应（ms ~ s）

**核心组件**：OpenEMS（边缘计算网关）

**工作流程**：

- STM32 将检测数据通过内部总线（CAN/SPI）上报本地 OpenEMS
- OpenEMS 运行本地控制闭环进行二次解算：
  - 确认硬件响应是否正确执行
  - 评估是否需要进一步调整
  - 记录 SOE（Sequence of Events）事件
  - 执行本地安全逻辑
- 响应时间：ms ~ s 级

**设计要点**：

- 本地控制闭环不依赖云端，断网时仍可运行
- 使用 RabbitMQ 进行本地消息传递
- 本地缓存时序数据，断网时暂存，恢复后自动同步

#### 9.3.3 第三级：云端级响应（s ~ min）

**核心组件**：ThingsBoard Server + 云端服务

**工作流程**：

- OpenEMS 将聚合后的状态通过 MQTT/TLS 上报云端
- 云端进行全局优化决策：
  - 更新报价策略
  - 调整调度计划
  - 记录事后分析
- 响应时间：s ~ min 级

**设计要点**：

- 云端崩溃不影响边缘端正常运行
- 云端恢复后自动同步边缘端数据
- 使用 Kafka 处理海量消息

### 9.5 状态同步机制

#### 9.5.1 断网重连同步

```
断网期间：
  边缘端 → 本地缓存时序数据（TimescaleDB轻量实例）
  边缘端 → 继续执行最后一帧有效指令
  边缘端 → 记录所有状态变更的变更日志（Change Log）

网络恢复：
  边缘端 → 发送变更日志到云端
  云端 → 回放变更日志，更新状态
  云端 → 下发最新调度指令
  边缘端 → 确认同步完成
```

#### 9.5.2 冲突解决策略

| 冲突场景               | 解决策略                                     |
| ---------------------- | -------------------------------------------- |
| 边缘端和云端状态不一致 | 以边缘端实际状态为准（边缘端更接近物理设备） |
| 调度指令冲突           | 以最新时间戳为准                             |
| 合同数据冲突           | 以云端数据为准（云端是合同数据权威来源）     |
| 计量数据冲突           | 以边缘端数据为准（边缘端是计量数据来源）     |

### 10.2 安全分区策略

| 安全分区  | 包含组件                      | 安全要求                         |
| --------- | ----------------------------- | -------------------------------- |
| **I区**   | OpenEMS, STM32, PCS           | 物理隔离，无网络连接，仅本地控制 |
| **II区**  | ThingsBoard Gateway, 本地缓存 | 物理网闸隔离，加密通信，入侵检测 |
| **III区** | 云端所有服务                  | 防火墙，WAF，安全审计，数据加密  |

### 10.3 物理网闸方案

| 网闸类型 | 方向     | 传输方式 | 延迟 | 可靠性 |
| -------- | -------- | -------- | ---- | ------ |
| 正向网闸 | I区→II区 | 单向光纤 | <7s  | >99.9% |
| 反向网闸 | II区→I区 | 单向光纤 | <12s | >99.9% |

### 10.4 加密方案

| 通信链路    | 加密协议       | 证书管理     | 密钥长度 |
| ----------- | -------------- | ------------ | -------- |
| 边缘端→云端 | TLS 1.3        | 国密SM2证书  | 256位    |
| 设备→边缘端 | TLS 1.2        | 设备证书     | 128位    |
| 内部总线    | 无（物理隔离） | -            | -        |
| 数据存储    | AES-256        | 密钥管理服务 | 256位    |
