## 1. 范围与规范性引用文件

### 1.1 范围

本标准规定了VPP 2.0本地能量管理系统（EMS）的架构设计、通信协议、调度算法、物理约束、安全合规和互操作要求。适用于：

- 分布式能源（DER）聚合商
- 充电桩运营平台
- 工商业储能系统
- 台区级能源管理节点
- 虚拟电厂（VPP）边缘计算节点

**目标设备形态**：本标准定义的能量路由器以**边缘计算节点（Edge Node）** 为物理载体，可部署于：

- 工业级嵌入式网关（如基于ARM/x86的工控机）
- 支持容器化部署的服务器
- 集成于智能配电终端的一体化设备

## 2. 术语与定义

### 2.1 核心术语

| 术语             | 英文                               | 定义                                                                                     |
| ---------------- | ---------------------------------- | ---------------------------------------------------------------------------------------- |
| **能源交换机**   | Energy Switch                      | 将EMS节点抽象为电力网络智能交换节点的架构范式，具备端口管理、带宽分配、路由决策能力      |
| **能量路由器**   | Energy Router (ER)                 | 部署于配电网边缘侧，具备数据采集、本地控制决策、多协议通信、多节点协同能力的智能终端设备 |
| **VPP 2.0**      | Virtual Power Plant 2.0            | 具备预测能力、经济博弈能力和合规结算能力的第二代虚拟电厂                                 |
| **台区**         | Transformer Area (TA)              | 配电变压器供电区域，是EMS调度的基本物理单元                                              |
| **带宽**         | Bandwidth                          | 台区变压器或线路的可用功率容量，类比网络交换机的背板带宽                                 |
| **NILM**         | Non-Intrusive Load Monitoring      | 非侵入式负载监测，通过总线电流/电压特征反推设备类型和状态                                |

| **头部识别码**   | Addressing Header                  | 消息头部中用于寻址和标识的结构化字段                                                     |
| **分级标签**     | Priority Tag (L1-L4)               | 设备重要程度的分级标识，用于QoS调度决策                                                  |
| **柔性可调资源** | Flexible Adjustable Resource (FAR) | 可通过能量路由器进行功率调节的终端设备，包括但不限于充电桩、储能系统、可控负荷           |
| **灵活性聚合**   | Aggregated Flexibility             | 能量路由器向VPP云端上报的、在未来时间窗口内可上调/下调的功率容量                         |
| **基线计算**     | Baseline Calculation               | 基于历史数据计算的"无调控状态下"的负荷曲线，用于VPP结算依据                              |
| **影子折旧**     | Shadow Depreciation                | 基于设备运行工况（充放电循环、暂态过载次数）计算的资产寿命损耗模型                       |
| **带宽配额**     | Bandwidth Quota                    | 台区变压器在当前物理约束下可分配给各端口的最大功率限额                                   |
| **电气距离**     | Electrical Distance                | 基于电压相关性、阻抗特性计算的节点间物理邻近度度量                                       |
| **拓扑版本号**   | Topology Version                   | 标识物理拓扑变更的版本计数器，用于多节点拓扑同步                                         |
| **信用权重**     | Credit Weight                      | 基于设备历史响应行为计算的调度优先级权重                                                 |

## 3. 核心架构范式

### 3.1 能源交换机模型

VPP_EMS采用"能源交换机"（Energy Switch）作为核心架构范式。EMS节点被抽象为电力网络的智能交换节点，具备以下核心能力：

| 交换机概念               | 电力系统映射       | 功能描述                                             |
| ------------------------ | ------------------ | ---------------------------------------------------- |
| **端口 (Port)**          | 设备接口           | 每个接入设备（充电桩、储能、逆变器）视为一个逻辑端口 |
| **背板带宽 (Backplane)** | 台区额定功率       | 变压器容量决定节点的最大总吞吐量                     |
| **MAC地址表**            | 设备指纹库         | NILM识别的设备特征指纹，用于身份确认                 |
| **QoS优先级**            | 分级标签           | L1-L4分级决定带宽分配优先级                          |
| **路由表**               | 电力路由表         | 节点间拓扑关系和路由代价                             |
| **流量整形**             | 斜率滤波           | 功率变化率控制，防止电压冲击                         |
| **拥塞控制**             | 协同减载           | 带宽不足时的有序减载机制                             |
| **生成树协议(STP)**      | 潮流冲突预防与仲裁 | 防止多节点同时倒送电导致母线过载                     |

### 3.2 数据流与控制流分离

系统严格分离数据平面（Data Plane）和控制平面（Control Plane）：

```
┌─────────────────────────────────────────────────────────┐
│                    控制平面 (Control Plane)               │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐ │
│  │调度指令  │  │策略配置  │  │紧急减载  │  │拓扑同步  │ │
│  └──────────┘  └──────────┘  └──────────┘  └──────────┘ │
│  优先级: 最高    确定性延迟: <10ms                        │
├─────────────────────────────────────────────────────────┤
│                    数据平面 (Data Plane)                  │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐ │
│  │设备状态  │  │时序数据  │  │历史数据  │  │事件日志  │ │
│  └──────────┘  └──────────┘  └──────────┘  └──────────┘ │
│  优先级: 普通    带宽: 尽力而为                           │
└─────────────────────────────────────────────────────────┘
```

### 3.3 数据流架构

能量路由器的数据流分为三个闭环：

**闭环一：实时控制环（毫秒级）**

```
传感器采样 → 物理约束校验 → 控制算法解算 → 指令下发 → 执行反馈
```

**闭环二：状态上报环（秒级）**

```
设备状态 → 数据聚合 → JSON-RPC推送 → 云端存储 → UI刷新
```

**闭环三：协同路由环（秒~分钟级）**

```
本地拓扑发现 → 邻居节点握手 → 带宽配额协商 → 路由表更新 → 云端同步
```

### 3.4 拓扑发现机制

节点间拓扑发现采用三种互补机制：

1. **电压相关性分析**：物理位置越近的节点，10kV侧电压波动相关性越高
2. **NILM事件对账**：节点间同步观测到的电力扰动事件，确认物理连接关系
3. **电力载波RSSI**：通过电力线注入识别信号，测量信号强度推算电气距离

### 3.5 路由表维护规范

路由表采用"本地发现+云端同步"的混合维护机制：

- **本地维护**：Edge节点维护热数据（当前物理连接最紧密的邻居）
- **云端同步**：Backend拼接全局拓扑，维护冷数据和资产数据
- **版本号机制**：物理线路变动时，Edge节点申请更新拓扑版本号
- **冲突处理**：以Edge节点的实时电气感知为最高优先级

## 4. 三层架构规范

### 4.1 架构总览

```
┌─────────────────────────────────────────────────────────────┐
│                    OpenEMS UI (应用展现层)                    │
│  可视化监控 | 配置管理 | 调试工具 | 报表分析                  │
├─────────────────────────────────────────────────────────────┤
│                    OpenEMS Backend (云端服务层)               │
│  数据聚合 | 元数据管理 | 多租户 | 历史存储 | 全局调度        │
├─────────────────────────────────────────────────────────────┤
│                    OpenEMS Edge (现场控制层)                  │
│  本地控制 | 硬件驱动 | 离线自治 | 实时解算 | 协议适配       │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 Edge（现场控制层）

**核心职责：**

- 毫秒级本地控制算法执行
- 硬件设备驱动和协议适配（Modbus/MQTT/OCPP）
- 离线自治运行（断网不中断控制）
- NILM实时分析和设备指纹识别
- SOE顺序事件记录
- 物理约束引擎（热容量、I²t、三相平衡、THD）

**技术要求：**

| 指标             | 要求               |
| ---------------- | ------------------ |
| 控制周期         | ≤ 1秒              |
| 离线运行时间     | ≥ 72小时           |
| 最大设备接入数   | ≥ 100个            |
| 本地日志存储     | ≥ 30天             |
| 1kHz采样数据处理 | 边缘侧完成特征提取 |
| 控制算法框架     | 6阶段周期循环      |

**控制周期（Cycle）执行流程：**

```
阶段1：读取所有通道(Channel)实时数据
阶段2：运行物理约束引擎（热容量、I²t、三相平衡、THD）
阶段3：运行控制算法（削峰填谷、自发自用、电价跟踪）
阶段4：生成各端口功率设定值(Setpoint)
阶段5：通过WriteHandler下发指令
阶段6：记录SOE日志
```

### 4.3 Backend（云端服务层）

**核心职责：**

- 多Edge节点数据聚合和持久化
- 元数据管理和设备资产登记
- 用户身份认证和权限管理
- 全局拓扑维护和路由表同步
- 历史数据分析和报表生成

**技术要求：**

| 指标                     | 要求         |
| ------------------------ | ------------ |
| 最大Edge节点在线数       | ≥ 10,000个   |
| 时序数据写入吞吐量       | ≥ 100万点/秒 |
| 元数据查询响应时间       | ≤ 100ms      |
| 多租户隔离               | 支持         |
| 全局拓扑版本号一致性检查 | 每15分钟     |

### 4.4 UI（应用展现层）

**核心职责：**

- 实时功率流向可视化
- 设备状态监控和告警
- 调度策略配置和下发
- 历史数据查询和图表展示
- 现场调试和诊断工具

**技术要求：**

| 指标               | 要求                           |
| ------------------ | ------------------------------ |
| 数据刷新延迟       | ≤ 1秒                          |
| 本地WiFi直连调试   | 支持                           |
| PWA离线缓存        | 支持                           |
| 多语言界面         | 支持                           |
| 拓扑可视化         | 支持图数据库拓扑展示           |
| 设备协议一致性中心 | 展示设备匹配状态和NILM校验结果 |

## 5. 功能要求

### 5.1 实时数据采集

能量路由器应具备以下数据采集能力：

| 采集类型 |    采样频率    | 数据项                                      |    接口协议     |
| -------- | :------------: | ------------------------------------------- | :-------------: |
| 电气量   | ≥1 kHz（推荐） | 三相电压、电流、有功/无功功率、功率因数     | Modbus TCP/RTU  |
| 电能质量 |     ≥1 kHz     | 谐波(THD)、电压偏差、频率偏差、三相不平衡度 | IEC 61000-4-30  |
| 设备状态 |      1 Hz      | 开关状态、告警码、运行模式                  |  Modbus / MQTT  |
| 环境量   |     0.1 Hz     | 环境温度（用于热容量修正）                  | Modbus / 4-20mA |
| 储能数据 |      1 Hz      | SOC、SOE、SOH、充放电循环次数               |  Modbus / CAN   |

**要求**：1 kHz采样数据应在边缘侧完成特征提取（FFT、RMS计算），仅将特征参数上传云端，原始波形按需本地缓存。

### 5.2 本地控制闭环

能量路由器应具备**断网独立运行**的本地控制能力，控制周期应≤1秒。

#### 5.2.1 控制算法框架

```
每个控制周期(Cycle)：
  阶段1：读取所有通道(Channel)实时数据
  阶段2：运行物理约束引擎（热容量、I²t、三相平衡、THD）
  阶段3：运行控制算法（削峰填谷、自发自用、电价跟踪）
  阶段4：生成各端口功率设定值(Setpoint)
  阶段5：通过WriteHandler下发指令
  阶段6：记录SOE日志
```

#### 5.2.2 设备分级标签（L1-L4）

能量路由器应对所有受控设备进行分级标签管理：

| 级别   | 名称                    | 编码 | 定义                             | 减载策略                                   | 典型设备                         |
| ------ | ----------------------- | :--: | -------------------------------- | ------------------------------------------ | -------------------------------- |
| **L1** | 核心负荷 (Critical)     | 0x01 | 断电将导致人身安全或重大财产损失 | **永不减载**，即使母线热容量触顶           | 医疗设备、安防系统、生命维持负荷 |
| **L2** | 保障负荷 (Guaranteed)   | 0x02 | 需要持续供电但允许短时功率压缩   | **按比例限流**，最大压缩不超过30%          | 关键办公、冷链物流、数据中心     |
| **L3** | 可延时负荷 (Deferrable) | 0x03 | 可在时间维度上平移的负荷         | **优先减载**，可完全切断或调低至最小功率   | 电动汽车充电桩、储能充电         |
| **L4** | 机会负荷 (Opportunity)  | 0x04 | 非必要、可随时中断的负荷         | **首选切断**，一旦触发任何约束立即释放带宽 | 景观照明、非紧急广告牌           |

**标签管理规则**：

- 标签应在设备注册时由系统管理员分配
- 能量路由器应通过NILM技术对标签进行**物理身份校验**，发现标签与实际负载特征不符时自动降级并告警
- 标签可在运行时动态调整（如参与调频服务的L3设备临时提升至L2优先级）

#### 5.2.3 动态标签调整机制

设备标签可根据以下因素动态调整：

1. **信用评分**：历史响应速度快的设备可获得标签升级
2. **NILM验证**：实际运行特征与标签声明不符时，自动降级
3. **辅助服务状态**：正在参与电网调频/调峰的设备临时升级
4. **紧急状态**：系统进入应急模式时，所有非L1设备降级

### 5.3 柔性减载策略

#### 5.3.1 减载触发条件

当以下任一条件满足时，能量路由器应启动减载流程：

1. **热容量越限**：当前功率超过变压器季节修正后的额定容量
2. **I²t积分超阈值**：暂态过载的累积热量超过安全限值
3. **电压质量恶化**：电压偏差超过±10%或THD超过8%
4. **三相不平衡超标**：三相电流不平衡度超过15%
5. **外部指令**：收到VPP云端或电网调度的减载指令

#### 5.3.2 减载执行次序

减载应按照以下次序分步执行，防止同步动作导致的电压过冲：

| 步骤 | 动作               | 延迟时间  | 目标设备             |    功率变化率限制    |
| :--: | ------------------ | :-------: | -------------------- | :------------------: |
|  1   | 切断L4级设备       |  T+0 ms   | 景观照明、非关键负荷 |   不限（瞬时切断）   |
|  2   | L3级设备限流至50%  |  T+50 ms  | 充电桩、储能充电     |   ≤20%额定功率/秒    |
|  3   | L3级设备限流至最小 | T+200 ms  | 充电桩、储能充电     |   ≤10%额定功率/秒    |
|  4   | L2级设备压缩至70%  | T+500 ms  | 关键办公、冷链       |    ≤5%额定功率/秒    |
|  5   | 紧急全切（保留L1） | T+1000 ms | 所有非L1设备         | 不限（仅限极端情况） |

**要求**：

- 每个步骤之间应引入基于节点ID哈希的**随机延迟（Jitter）**，偏移范围为0~50ms，防止多台区同步动作
- 每个步骤执行后应通过实时通道验证功率是否真实下降，若未响应则在10ms内执行下一级动作
- 减载完成后应生成完整的SOE记录

### 5.4 预测与基线

#### 5.4.1 预测类型与精度要求

| 预测类型     | 预测周期     | 精度要求   | 更新频率 | 算法建议                |
| ------------ | ------------ | ---------- | -------- | ----------------------- |
| 光伏出力预测 | 超短期(5min) | MAE < 10%  | 每5分钟  | LSTM + 物理约束         |
| 光伏出力预测 | 短期(24h)    | MAE < 15%  | 每小时   | 数值天气预报 + 物理模型 |
| 负荷预测     | 超短期(5min) | MAPE < 10% | 每5分钟  | LSTM + 物理约束         |
| 负荷预测     | 短期(24h)    | MAPE < 15% | 每小时   | 时序分解 + 相似日匹配   |
| 电价预测     | 短期(24h)    | MAPE < 20% | 每天     | 市场模型 + 时间序列     |
| 灵活性预测   | 短期(24h)    | MAE < 15%  | 每小时   | 基于设备状态的概率模型  |

#### 5.4.2 基线计算算法

VPP结算依赖基线（Baseline）计算，要求：

- **数据窗口**：最近30天历史数据
- **计算方法**：取最近10个相似日（同类型日、同天气条件）的负荷数据，剔除最高和最低值后取平均
- **异常剔除**：自动识别并剔除异常日（节假日、故障日）
- **天气修正**：结合天气预报进行基线修正
- **输出频率**：每15分钟输出一个基线值
- **更新频率**：每日自动更新，支持人工修正

#### 5.4.3 预测接口规范

    "horizon": "SHORT_TERM",

    }

### 5.5 离线自治

当能量路由器与云端连接中断时，应自动切换至**离线自治模式**：

| 功能           |  在线模式  | 离线模式                   |
| -------------- | :--------: | -------------------------- |
| 本地控制闭环   | ✓ 正常运行 | ✓ 正常运行                 |
| 云端指令接收   |     ✓      | ✗（使用最后一次有效指令）  |
| 拓扑发现与同步 | ✓ 实时同步 | ✓ 本地缓存，恢复后断点续传 |
| 带宽预借       | ✓ 云端授权 | ✓ 基于信用权重的本地预借   |
| SOE记录        | ✓ 实时上传 | ✓ 本地缓存，恢复后批量上传 |
| 基线更新       | ✓ 云端辅助 | ✓ 本地独立计算             |
| 固件升级       |     ✓      | ✗                          |

**离线恢复**：网络恢复后，能量路由器应在30秒内完成与云端的全量数据同步。

### 5.6 NILM与AnomAlert融合

#### 5.6.1 NILM功能要求

能量路由器应集成非侵入式负载监测（NILM）能力：

- **采样要求**：≥1 kHz，三相电压/电流同步采样
- **识别能力**：至少能识别充电桩启动、储能充放电、大型电机启停、空调压缩机等典型设备事件
- **识别延迟**：从事件发生到输出识别结果应≤200ms
- **识别准确率**：在典型台区环境下应≥90%

#### 5.6.2 AnomAlert异常识别

借鉴AnomAlert的机械诊断逻辑，能量路由器应具备以下异常识别能力：

| 异常类型         | 检测方法                  | 响应动作                             |
| ---------------- | ------------------------- | ------------------------------------ |
| 设备启动涌流异常 | 电流上升斜率(di/dt)超阈值 | 标记设备为"亚健康"，降低其调度优先级 |
| 谐波特征突变     | 特定次谐波幅值偏离基线    | 触发电能质量告警，限制非线性负载接入 |
| 接触不良/微弧    | 高频噪声分量异常          | 触发设备检修告警，记录SOE            |
| 电容老化         | 功率因数偏移特征          | 建议更换设备，调整无功补偿策略       |
| 三相不平衡恶化   | 中性点电流持续上升        | 触发负载迁移或限流                   |

#### 5.6.3 物理身份校验

能量路由器应利用NILM技术对设备的分级标签进行**物理身份校验**：

```
流程：
1. 设备注册时记录其电气指纹（V-I轨迹、谐波特征、启动斜率）
2. 运行时持续监测该设备的实际电气特征
3. 若实际特征与注册指纹偏差超过阈值：
   a. 自动降低该设备的信用权重
   b. 触发告警："设备标签与物理身份不符"
   c. 将该设备从高优先级队列移除
```

### 6.4 头部识别码规范

#### 6.4.1 协议帧头部结构

能量路由器的所有JSON-RPC消息应包含自定义头部字段，采用**8字节精简头部 + 扩展字段**结构：

**标准头部（8字节）：**

```
┌─────────┬─────────┬─────────┬─────────┬─────────┬─────────┬─────────┬─────────┐
│ 台区ID  │ 台区ID  │ 台区ID  │ 台区ID  │ 支路ID  │ 支路ID  │ 设备类别 │ 保留字节 │
│  Byte0  │  Byte1  │  Byte2  │  Byte3  │  Byte4  │  Byte5  │  Byte6  │  Byte7  │
└─────────┴─────────┴─────────┴─────────┴─────────┴─────────┴─────────┴─────────┘
```

**字段定义：**

| 字段     |  长度   | 类型   | 说明                    |
| -------- | :-----: | ------ | ----------------------- |
| 台区ID   | 4 bytes | UInt32 | 全局唯一台区标识符      |
| 支路ID   | 2 bytes | UInt16 | 台区内支路编号          |
| 设备类别 | 1 byte  | Enum   | 设备类型编码（见附录A） |
| 保留字节 | 1 byte  | Hex    | 预留扩展字节            |

**扩展字段（JSON-RPC params.**header**中携带）：**

| 字段               |   长度   | 类型    | 说明                           |
| ------------------ | :------: | ------- | ------------------------------ |
| `protocol_version` | 4 bytes  | String  | 协议版本号，当前为"1.0"        |
| `target_id`        | 32 bytes | String  | 目标设备唯一标识（字符串格式） |
| `priority_tag`     |  1 byte  | Enum    | 设备分级标签：L1/L2/L3/L4      |
| `reserved_byte`    |  1 byte  | Hex     | 预留扩展字节（与标准头部同步） |
| `timestamp`        | 8 bytes  | Int64   | Unix毫秒时间戳                 |
| `ttl`              | 2 bytes  | UInt16  | 指令生存时间（毫秒）           |
| `topology_version` | 4 bytes  | UInt32  | 发送方当前的拓扑版本号         |
| `credit_weight`    | 4 bytes  | Float32 | 发送方信用权重（0.0~1.0）      |

#### 6.4.2 设备寻址格式（Target_ID）

```
格式：[台区ID]-[支路ID]-[设备类别]-[设备序号]

示例：
TA-001-BR-003-EVCS-007
│      │      │       └── 设备序号：007号
│      │      └────────── 设备类别：EVCS(充电桩)
│      └───────────────── 支路ID：003号支路
└──────────────────────── 台区ID：001号台区

设备类别编码：
- EVCS：电动汽车充电桩
- ESS：储能系统
- PV：光伏逆变器
- MET：智能电表
- HVAC：暖通空调
- LIGHT：照明
- OTHER：其他
```

#### 6.4.3 保留字节（Reserved Byte）定义

预留字节（1 Byte, 8 bits）用于未来功能扩展：

|  Bit位  | 用途           | 说明                                    | 扩展计划 |
| :-----: | -------------- | --------------------------------------- | :------: |
|  Bit 0  | 绿色能源标识   | 1=当前电能来自绿电（光伏/风电），0=常规 |   v1.0   |
|  Bit 1  | V2G模式标识    | 1=设备处于V2G放电模式，0=充电/待机      |   v1.0   |
|  Bit 2  | 调频服务标识   | 1=设备正在参与快速调频(FFR)服务         |   v1.0   |
|  Bit 3  | 碳配额标识     | 1=该指令涉及碳配额交易，0=常规调度      |   v1.1   |
|  Bit 4  | 资产归属权标识 | 1=跨业主资产，0=单一业主                |   v1.1   |
| Bit 5-7 | 保留           | 留作未来扩展                            |   未来   |

**扩展规则**：新增功能应优先使用预留字节中的空闲位，避免修改协议帧结构。

#### 6.4.4 寻址模式

- **单播**：精确匹配台区ID+支路ID+设备类别
- **组播**：匹配台区ID+支路ID，设备类别=0x00
- **广播**：台区ID=0xFFFFFFFF

### 6.5 设备注册与身份声明

#### 6.5.1 注册流程

```
设备上电 → 发送注册请求(含设备ID、型号、额定功率、协议版本)
    ↓
Edge接收请求 → 校验设备合法性(白名单/证书)
    ↓
Edge分配本地设备ID → 记录设备指纹(电气特征)
    ↓
Edge向Backend上报设备注册信息
    ↓
Backend确认 → 返回注册成功(含拓扑版本号)
    ↓
设备进入在线状态 → 开始周期性数据上报
```

**注册请求格式：**

```json
{
  "method": "deviceRegister",
  "params": {
    "device_id": "evcs_007",
    "device_model": "EVSE-AC-7kW-v3",
    "rated_power_w": 7000,
    "protocol_version": "1.0",
    "capabilities": ["CHARGE", "LIMIT", "SHED"],
    "priority_tag": "L3",
    "electrical_fingerprint": {
      "v_i_trajectory_hash": "a1b2c3d4e5f6",
      "startup_slope": 45.2,
      "harmonic_profile": [3.2, 1.1, 0.5, 0.3]
    }
  }
}
```

**注册响应格式：**

```json
{
  "jsonrpc": "2.0",
  "result": {
    "status": "registered",
    "local_device_id": "TA-001-BR-003-EVCS-007",
    "topology_version": 42,
    "heartbeat_interval_s": 30,
    "assigned_bandwidth_w": 7000
  }
}
```

#### 6.5.2 身份声明机制

能量路由器应支持两种身份声明模式：

**模式一：主动声明（Active Declaration）**

设备上电后主动向Edge发送身份声明报文，包含设备ID、型号、额定功率、协议版本、能力集和电气指纹。Edge在接收到声明后执行以下校验：

1. **白名单校验**：设备ID是否在预注册白名单中
2. **证书校验**：设备证书是否有效（如启用TLS双向认证）
3. **指纹校验**：设备声明的电气指纹是否与NILM实时采集的特征匹配
4. **带宽校验**：设备额定功率是否超过台区剩余可用带宽

**模式二：被动发现（Passive Discovery）**

对于不支持主动声明的传统设备，Edge应通过NILM技术进行被动发现：

1. Edge持续监测总线电流/电压波形
2. 当检测到新设备启动特征（特定V-I轨迹、启动涌流斜率）时
3. 自动创建虚拟设备记录，分配临时设备ID
4. 通过UI提示运维人员确认设备身份和分级标签
5. 运维人员确认后，设备进入正式管理状态

**身份声明报文格式：**

```json
{
  "method": "declareIdentity",
  "params": {
    "device_id": "evcs_007",
    "device_type": "EVCS",
    "manufacturer": "ExampleEVSE",
    "firmware_version": "3.2.1",
    "rated_power_w": 7000,
    "min_power_w": 1400,
    "power_step_w": 100,
    "protocol_version": "1.0",
    "capabilities": {
      "charge": true,
      "discharge": false,
      "power_limit": true,
      "shed": true,
      "ramp_rate_control": true,
      "phase_switching": false,
      "v2g": false
    },
    "priority_tag": "L3",
    "electrical_fingerprint": {
      "v_i_trajectory_hash": "a1b2c3d4e5f6",
      "startup_slope_A_per_s": 45.2,
      "harmonic_profile_pct": [3.2, 1.1, 0.5, 0.3],
      "power_factor_range": [0.85, 0.99]
    }
  }
}
```

#### 6.5.3 心跳与保活

已注册设备应定期发送心跳报文以维持在线状态：

| 参数         | 要求                                |
| ------------ | ----------------------------------- |
| 心跳间隔     | ≤ 30秒                              |
| 心跳超时判定 | 连续3次未收到                       |
| 超时后动作   | 标记为离线                          |
| 离线后恢复   | 重新发送注册请求                    |
| 心跳内容     | 设备ID + 时间戳 + 当前功率 + 状态码 |

**心跳报文格式：**

```json
{
  "method": "heartbeat",
  "params": {
    "device_id": "TA-001-BR-003-EVCS-007",
    "timestamp": 1715218372000,
    "current_power_w": 3500,
    "status_code": 0,
    "fault_code": 0
  }
}
```

## 7. 物理约束与安全模型

### 7.1 物理约束引擎

能量路由器应内置物理约束引擎，作为所有调度决策的硬性边界。约束引擎在每控制周期中运行，确保所有指令不超出物理安全红线。

#### 7.1.1 热容量约束

变压器和线路的热容量是能量路由器的核心物理约束：

**静态额定功率**：变压器铭牌额定容量 $S_{rated}$

**季节性修正**：

$$S_{max}(T) = S_{rated} \times k_{season}(T)$$

其中 $k_{season}(T)$ 为基于环境温度的修正系数：

|  环境温度范围   | 修正系数 $k_{season}$  |
| :-------------: | :--------------------: |
|    T ≤ 25°C     |          1.00          |
| 25°C < T ≤ 35°C | 1.00 - 0.01 × (T - 25) |
| 35°C < T ≤ 40°C | 0.90 - 0.02 × (T - 35) |
|    T > 40°C     |          0.80          |

**安全裕度**：所有调度决策应在 $S_{max}$ 的90%以内运行，预留10%作为瞬时冲击缓冲。

#### 7.1.2 I²t暂态过载约束

能量路由器应监控暂态过载的累积热效应：

$$I^2t = \int_{t_0}^{t_1} i(t)^2 dt$$

- **短时过载允许**：额定电流120%以内，持续时间不超过30秒
- **积分惩罚**：每次过载事件记录I²t值，累积超过阈值时触发强制减载
- **冷却恢复**：过载解除后，需经过冷却时间才能恢复满功率运行

#### 7.1.3 电压质量约束

| 参数        | 正常范围 | 告警阈值 | 动作阈值 |
| ----------- | -------- | -------- | -------- |
| 电压偏差    | ±5%      | ±7%      | ±10%     |
| 频率偏差    | ±0.2Hz   | ±0.5Hz   | ±1.0Hz   |
| THD（电压） | <5%      | 5%~8%    | >8%      |
| THD（电流） | <8%      | 8%~12%   | >12%     |

#### 7.1.4 三相不平衡约束

- **正常范围**：三相电流不平衡度 < 10%
- **告警阈值**：10% ~ 15%
- **动作阈值**：> 15%（触发负载迁移或限流）

#### 7.1.5 约束优先级

当多个约束同时触发时，按以下优先级处理：

1. **最高**：电压质量约束（直接影响设备安全）
2. **高**：热容量约束（影响变压器寿命）
3. **中**：I²t暂态过载约束（累积热效应）
4. **低**：三相不平衡约束（影响电能质量）

### 7.3 影子折旧模型

能量路由器应内置资产寿命跟踪模型，将调度操作对设备寿命的影响量化为"影子折旧"成本。

#### 7.3.1 折旧因子

| 操作类型            | 折旧因子 | 说明             |
| ------------------- | :------: | ---------------- |
| 正常充放电循环      |   1.0×   | 基准折旧率       |
| 深度放电（SOC<20%） |   2.0×   | 加速老化         |
| 快充（>1C倍率）     |   1.5×   | 加速老化         |
| 暂态过载事件        |   3.0×   | 显著影响设备寿命 |
| 三相不平衡运行      |   1.2×   | 长期影响         |
| 高温运行（>40°C）   |   1.5×   | 加速老化         |

#### 7.3.2 折旧计算

$$Depreciation_{total} = \sum (Operation_i \times Factor_i)$$

- 每次调度操作记录折旧贡献值
- 累计折旧超过设备设计寿命的80%时触发告警
- 折旧数据作为调度决策的"成本"输入，用于优化算法

#### 7.3.3 折旧报告

能量路由器应定期生成资产折旧报告，包含：

- 各设备的累计折旧值
- 预计剩余寿命
- 高折旧操作统计
- 优化建议（如调整充放电策略可延长寿命XX%）

## 8. 调度算法与优化引擎

### 8.1 调度算法框架

能量路由器的调度算法采用分层架构，从底层安全保护到上层经济优化：

```
┌─────────────────────────────────────────────────────────────┐
│                   经济优化层 (Economic Layer)                 │
│  电价跟踪 | 套利策略 | 碳排放优化 | 需求响应投标            │
├─────────────────────────────────────────────────────────────┤
│                   策略执行层 (Policy Layer)                   │
│  削峰填谷 | 自发自用 | 需量管理 | 柔性减载                  │
├─────────────────────────────────────────────────────────────┤
│                   物理约束层 (Constraint Layer)               │
│  热容量 | I²t | 电压质量 | 三相平衡 | 设备保护              │
└─────────────────────────────────────────────────────────────┘
```

### 8.2 物理约束层

物理约束层是调度算法的最底层，确保所有指令不超出物理安全红线。详见[第7章](#7-物理约束与安全模型)。

### 8.3 策略执行层

#### 8.3.1 削峰填谷策略

**目标**：将台区最大需量控制在设定阈值以下，同时在低谷时段增加负荷。

**算法逻辑**：

```
每个控制周期：
  1. 读取当前总功率 P_total
  2. 如果 P_total > P_peak_threshold：
     a. 计算需削减功率 ΔP = P_total - P_peak_threshold
     b. 按L4→L3→L2顺序分配减载任务
     c. 下发限流指令（带斜率限制）
  3. 如果 P_total < P_valley_threshold：
     a. 计算可增加功率 ΔP = P_valley_threshold - P_total
     b. 按L3→L4顺序分配充电任务
     c. 下发增载指令
```

#### 8.3.2 自发自用策略

**目标**：最大化本地光伏消纳，减少向电网购电。

**算法逻辑**：

```
每个控制周期：
  1. 读取光伏出力 P_pv 和本地负荷 P_load
  2. 计算净功率 P_net = P_pv - P_load
  3. 如果 P_net > 0（光伏有余）：
     a. 优先给储能充电（SOC < 95%）
     b. 储能满后，给L3级充电桩增载
     c. 仍有剩余则向电网馈电
  4. 如果 P_net < 0（光伏不足）：
     a. 优先从储能放电（SOC > 20%）
     b. 储能不足时，从电网购电
     c. 必要时对L3/L4设备限流
```

#### 8.3.3 需量管理策略

**目标**：控制台区最大需量，避免触发基本电费罚款。

**算法逻辑**：

```
每个控制周期：
  1. 读取当前滚动15分钟需量 D_current
  2. 如果 D_current > D_target × 0.9（接近需量阈值）：
     a. 预测本周期剩余时间的需量趋势
     b. 如果预测将超过阈值，提前启动减载
     c. 减载优先级：L4 → L3 → L2
  3. 需量周期结束后，重置计数器
```

### 8.4 经济优化层

#### 8.4.1 电价跟踪策略

**目标**：在分时电价或动态电价环境下，通过充放电调度实现电费最优。

**算法逻辑**：

```
每个控制周期：
  1. 获取当前电价 price_now 和未来24小时电价曲线
  2. 如果 price_now < price_low_threshold：
     a. 启动储能充电（SOC < 95%）
     b. 启动L3级设备充电
  3. 如果 price_now > price_high_threshold：
     a. 启动储能放电（SOC > 20%）
     b. 对L3/L4设备限流或切断
  4. 如果 price_now 在中间区间：
     a. 按自发自用策略运行
```

#### 8.4.2 多时步前瞻优化

能量路由器应支持基于混合整数线性规划（MILP）或启发式算法的多时步优化：

**输入**：

- 未来24小时电价曲线
- 光伏出力预测
- 负荷预测
- 储能SOC状态
- 设备约束（充放电功率限制、效率曲线）

**输出**：

- 最优充放电计划（15分钟粒度）
- 各端口功率设定值序列
- 预期电费/收益

**优化目标**（可配置）：

- 最小化电费支出
- 最大化光伏消纳
- 最小化碳排放
- 最大化套利收益

#### 8.4.3 灵活性聚合与上报

能量路由器应实时计算并向VPP云端上报灵活性聚合容量：

**上报内容**：

```json
{
  "method": "reportFlexibility",
  "params": {
    "timestamp": 1715218372000,
    "window_start": 1715218372000,
    "window_end": 1715220172000,
    "baseline_power_w": 150000,
    "flexibility_up_w": 50000,
    "flexibility_down_w": 80000,
    "flexibility_up_duration_s": 300,
    "flexibility_down_duration_s": 600,
    "confidence_pct": 85,
    "constraints": {
      "thermal_headroom_w": 30000,
      "battery_available_w": 20000,

    }

```

**计算逻辑**：

```
灵活性上调容量 = 当前可削减的L3/L4设备总功率 + 储能可放电功率
灵活性下调容量 = 当前可增加的L3设备充电功率 + 储能可充电功率
```

### 8.5 曲线跟踪控制器

#### 8.5.1 功能要求

能量路由器应支持接收VPP云端下发的功率跟踪曲线 $P_{target}(t)$，并在本地执行精确跟踪：

**曲线格式**：

```json
{
  "method": "setCurveTarget",
  "params": {
    "curve_id": "curve-20260509-001",
    "start_time": 1715218372000,
    "end_time": 1715220172000,
    "resolution_s": 300,
    "points": [
      { "t": 0, "p_w": 150000 },
      { "t": 300, "p_w": 145000 },
      { "t": 600, "p_w": 140000 }
    ],
    "tolerance_pct": 5,
    "ramp_rate_limit_pct_per_s": 2
  }
}
```

#### 8.5.2 跟踪算法

```
每个控制周期：
  1. 根据当前时间计算目标功率 P_target(t)
  2. 读取实际功率 P_actual
  3. 计算偏差 ΔP = P_target - P_actual
  4. 如果 |ΔP| > P_target × tolerance_pct：
     a. ΔP > 0：增加L3设备功率或储能放电
     b. ΔP < 0：削减L3/L4设备功率或储能充电
  5. 下发调节指令（带斜率限制）
  6. 记录跟踪偏差到SOE日志
```

#### 8.5.3 偏差修正

- **实时偏差**：每秒比对实际功率与目标曲线，进行毫秒级修偏
- **累积偏差**：每15分钟计算累积能量偏差，在后续时段补偿
- **偏差上报**：跟踪偏差超过容忍度时，立即上报VPP云端

### 9.3 拓扑发现协议

#### 9.3.1 电压相关性发现

节点间通过电压波动相关性分析自动发现物理邻近关系：

```
每个节点：
  1. 持续记录本地电压特征值（1秒分辨率）
  2. 每5分钟生成电压波动指纹（过去5分钟的ΔV曲线）
  3. 通过组播广播电压指纹
  4. 接收邻居节点的电压指纹
  5. 计算互相关性系数 ρ
  6. 如果 ρ > 0.85：判定为物理邻近节点
  7. 更新本地邻居表
```

#### 9.3.2 NILM事件对账

节点间通过同步观测到的电力扰动事件确认物理连接：

```
当节点A检测到本地大功率设备启动事件：
  1. 记录事件时间戳和特征指纹
  2. 通过协同通道广播事件通知
  3. 节点B接收到通知后，比对本地观测到的扰动
  4. 如果时间戳和特征匹配：
     a. 确认A和B处于同一条10kV支路
     b. 记录电气距离（基于扰动衰减程度）
```

#### 9.3.3 拓扑版本号管理

| 操作       | 触发条件             | 动作                                 |
| ---------- | -------------------- | ------------------------------------ |
| 版本号递增 | 检测到物理拓扑变更   | 本地版本号+1，通知邻居节点           |
| 版本号同步 | 节点上线或网络恢复   | 向邻居节点请求最新版本号             |
| 版本号冲突 | 两个节点版本号不一致 | 以较高版本号为准，低版本节点同步更新 |
| 版本号广播 | 版本号变更           | 通过组播向所有邻居节点广播新版本号   |
| 云端同步   | 版本号变更           | 向Backend上报新版本号和变更摘要      |

### 9.4 带宽协商协议

#### 9.4.1 带宽配额声明

每个能量路由器应定期向邻居节点声明自己的带宽使用状态：

```json
{
  "method": "declareBandwidth",
  "params": {
    "node_id": "TA-001",
    "timestamp": 1715218372000,
    "transformer_rated_va": 315000,
    "seasonal_max_va": 283500,
    "current_load_va": 180000,
    "reserved_critical_va": 50000,
    "available_quota_va": 53500,
    "forecast_load_15min_va": 200000,
    "credit_weight": 0.85,
    "topology_version": 42
  }
}
```

#### 9.4.2 带宽预借机制

当节点需要临时超出本地配额时，可向邻居节点发起带宽预借请求：

```
请求节点：
  1. 计算本地带宽赤字 ΔP
  2. 查询邻居节点的可用配额
  3. 向信用权重最高的邻居发起预借请求
  4. 等待确认（超时时间：100ms）
  5. 如果确认：使用预借带宽
  6. 如果拒绝或超时：启动本地减载

响应节点：
  1. 收到预借请求
  2. 检查本地当前负荷和预测负荷
  3. 如果有余量：确认预借，锁定配额
  4. 如果无余量：拒绝请求
  5. 如果本地负荷突增：收回预借配额
```

#### 9.4.3 信用权重计算

信用权重基于设备历史行为动态计算：

$$Credit = 0.4 \times ResponseRate + 0.3 \times Accuracy + 0.2 \times Availability + 0.1 \times Age$$

| 因子         | 计算方式                                    | 权重 |
| ------------ | ------------------------------------------- | :--: |
| ResponseRate | 过去100次指令的响应成功率                   | 0.4  |
| Accuracy     | 过去100次响应的功率偏差（偏差越小得分越高） | 0.3  |
| Availability | 过去24小时的在线率                          | 0.2  |
| Age          | 设备在线天数（每30天+0.1，上限1.0）         | 0.1  |

### 9.5 协同减载协议

#### 9.5.1 减载请求广播

当节点检测到带宽赤字且本地减载不足以解决问题时，发起协同减载：

```json
{
  "method": "requestCoordinatedShed",
  "params": {
    "requestor_id": "TA-001",
    "timestamp": 1715218372000,
    "required_shed_w": 50000,
    "urgency": "HIGH",
    "timeout_ms": 100,
    "reason": "THERMAL_OVERLOAD"
  }
}
```

#### 9.5.2 协同响应

邻居节点收到减载请求后，评估自身可贡献的减载容量：

```json
{
  "method": "respondCoordinatedShed",
  "params": {
    "responder_id": "TA-002",
    "request_id": "shed-20260509-001",
    "can_shed_w": 30000,
    "shed_cost": 150,
    "estimated_duration_s": 600,
    "affected_devices": ["L3", "L4"]
  }
}
```

#### 9.5.3 减载仲裁

根节点（或请求节点）根据响应结果进行仲裁：

1. 收集所有邻居节点的响应
2. 按减载成本（shed_cost）从低到高排序
3. 选择成本最低的组合满足减载需求
4. 向选中的节点发送确认指令
5. 向未选中的节点发送取消指令
6. 记录完整的协同减载SOE
