## 1. 概述

需求响应（Demand Response, DR）是 VPP 系统与电网公司之间的核心交互场景。电网公司通过 DR 信号向 VPP 聚合商下发削峰填谷指令，VPP 系统接收后将其转换为内部调度指令，驱动储能充放电、充电桩功率调节、空调负荷控制等资源响应。

本方案支持两种 DR 信号接收通道：**OpenADR 2.0**（国际标准互联网通道）和**电力专用通道**（电力行业专网通道）。两种通道在协议标准、通信方式、安全等级、部署成本等方面存在显著差异，适用于不同的电网公司和业务场景。

| 对比维度     | OpenADR 2.0                    | 电力专用通道                   |
| ------------ | ------------------------------ | ------------------------------ |
| **标准性质** | 国际开放标准（IEC 62746-10-1） | 中国电力行业专有协议           |
| **通信网络** | 互联网 / VPN                   | 电力专网（SDH/OTN）            |
| **安全等级** | TLS 1.2+ / X.509 证书          | 物理隔离 + 国密加密            |
| **部署成本** | 低（软件部署，无需额外硬件）   | 高（需物理隔离装置、专网接入） |
| **实时性**   | 秒~分钟级                      | 秒级                           |
| **互操作性** | 高（国际通用，多厂商互通）     | 低（各省电网公司实现各异）     |
| **国内应用** | 部分试点（江苏、上海等）       | 主流（国网/南网标准）          |

## 2. OpenADR 2.0 详解

### 2.1 标准概述

**OpenADR 2.0**（Open Automated Demand Response）是由美国劳伦斯伯克利国家实验室（LBNL）发起、经 IEC 标准化为 **IEC 62746-10-1** 的开放自动需求响应标准。目前最新版本为 **OpenADR 2.0b**，定义了需求响应信号的标准化交互模型和通信协议。

| 项目           | 内容                                                       |
| -------------- | ---------------------------------------------------------- |
| **标准编号**   | IEC 62746-10-1 / OpenADR 2.0b                              |
| **制定组织**   | OpenADR Alliance（LBNL 发起，2010 年成立）                 |
| **标准化状态** | IEC 国际标准（2018 年发布）                                |
| **国内对标**   | GB/T 36343-2018《信息技术 自动需求响应系统通用技术要求》   |
| **核心用途**   | 电网公司（VTN）向 VPP/用户（VEN）下发 DR 事件信号          |
| **通信协议**   | HTTP / HTTPS（RESTful API + XML/JSON 载荷）                |
| **安全机制**   | TLS 1.2+、X.509 证书双向认证、数字签名                     |
| **成熟度**     | 国际广泛部署（美国 PJM/CAISO、欧洲 ENTSO-E、日本、韩国等） |

### 2.2 核心角色：VTN 与 VEN

OpenADR 2.0 定义了两种核心角色：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  VTN（Virtual Top Node，虚拟顶层节点）                                       │
│  角色：DR 信号的发布者（电网公司 / 独立系统运营商）                           │
│  职责：                                                                     │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │  • 创建和管理 DR 事件（Event）                                       │  │
│  │  • 向注册的 VEN 发布 DR 信号                                        │  │
│  │  • 接收 VEN 的响应状态回传                                          │  │
│  │  • 评估 DR 事件执行效果                                              │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                    │                                         │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │  OpenADR 2.0b 通信协议（HTTP/HTTPS + XML/JSON）                      │  │
│  │  • 轮询（Poll）：VEN 定期向 VTN 查询是否有新事件                     │  │
│  │  • 推送（Push）：VTN 主动向 VEN 推送事件（需 VEN 支持 HTTP Server）  │  │
│  │  • 报告（Report）：VEN 向 VTN 回传资源状态和响应结果                  │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                    │                                         │
│  VEN（Virtual End Node，虚拟末端节点）                                       │
│  角色：DR 信号的接收者和响应者（VPP 聚合商 / 大用户 / 负荷聚合商）           │
│  职责：                                                                     │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │  • 注册到 VTN，订阅 DR 事件                                         │  │
│  │  • 接收 DR 信号并解析为内部调度指令                                 │  │
│  │  • 回传资源状态、响应容量和执行结果                                  │  │
│  │  • 支持多 VTN 注册（不同电网公司/市场）                             │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 2.3 核心数据模型

OpenADR 2.0b 定义了以下核心数据对象：

#### 2.3.1 DR 事件（Event）

DR 事件是 VTN 向 VEN 下发的最核心信息，包含以下关键字段：

| 字段                   | 类型     | 说明                                                            | 示例值                           |
| ---------------------- | -------- | --------------------------------------------------------------- | -------------------------------- |
| **eventID**            | string   | 事件唯一标识符                                                  | `"DR-20260526-001"`              |
| **modificationNumber** | integer  | 事件修改版本号（支持事件更新/取消）                             | `0`（初始版本）                  |
| **eventStatus**        | enum     | 事件状态：`FAR`（远期）/ `NEAR`（近期）/ `ACTIVE` / `CANCELLED` | `"ACTIVE"`                       |
| **createdDateTime**    | datetime | 事件创建时间                                                    | `"2026-05-26T08:00:00Z"`         |
| **eventStart**         | datetime | 事件开始时间                                                    | `"2026-05-26T14:00:00Z"`         |
| **eventEnd**           | datetime | 事件结束时间                                                    | `"2026-05-26T16:00:00Z"`         |
| **priority**           | integer  | 事件优先级（1=最高，越低越紧急）                                | `1`                              |
| **targets**            | array    | 目标资源列表（VEN ID / 资源类型 / 地理位置）                    | `[{"venID": "VPP_SICHUAN_001"}]` |
| **intervals**          | array    | 时段列表（每个时段包含 duration 和 signal 值）                  | 见下方示例                       |

**Interval（时段）结构**：

| 字段              | 类型     | 说明                  | 示例值                 |
| ----------------- | -------- | --------------------- | ---------------------- |
| **duration**      | duration | 该时段持续时间        | `"PT1H"`（1 小时）     |
| **signalPayload** | float    | 该时段的信号值        | `500.0`（单位：kW）    |
| **signalType**    | enum     | 信号类型（见 §2.3.2） | `"x-sichuan-dr-level"` |

#### 2.3.2 信号类型（Signal Type）

OpenADR 2.0b 预定义了多种标准信号类型，同时支持自定义扩展：

| 信号类型                   | 说明                   | 在本方案中的用途             |
| -------------------------- | ---------------------- | ---------------------------- |
| **SIMPLE**                 | 简单开/关信号          | 基础 DR 事件触发             |
| **ELECTRICITY_PRICE**      | 实时电价信号           | 经济型 DR（价格驱动）        |
| **ENERGY_PRICE**           | 能量价格               | 与现货市场联动               |
| **DEMAND_CHARGE**          | 需量电费信号           | 需量管理触发                 |
| **LOAD_CONTROL**           | 负荷控制信号           | 直接负荷控制（空调/热水器）  |
| **LOAD_DISPATCH**          | 负荷调度信号           | VPP 资源调度                 |
| **x-sichuan-dr-level**     | 四川 DR 等级（自定义） | 四川电网保供电等级（1-5 级） |
| **x-sichuan-tie-line-atc** | 联络线 ATC（自定义）   | 陇电入川联络线可用容量       |

#### 2.3.3 报告（Report）

VEN 向 VTN 回传的报告包含以下关键信息：

| 报告类型                   | 说明              | 上报频率     |
| -------------------------- | ----------------- | ------------ |
| **METADATA_HISTORY_USAGE** | 历史用电/发电数据 | 日级         |
| **METADATA_CURRENT_USAGE** | 当前功率/能量数据 | 分钟级       |
| **REPORT_OPT_IN**          | 自愿参与 DR 事件  | 事件触发时   |
| **REPORT_OPT_OUT**         | 退出 DR 事件      | 事件触发时   |
| **REPORT_ACTIVE**          | 正在执行 DR 事件  | 事件执行期间 |
| **REPORT_COMPLETED**       | DR 事件执行完成   | 事件结束后   |
| **REPORT_FAILED**          | DR 事件执行失败   | 事件执行期间 |

### 2.6 在本方案中的部署架构（安全加固版）

> **⚠️ 安全设计说明**：OpenADR 2.0 基于互联网/VPN 通信，属于通用 IT 协议。根据等保 2.0 三级要求（GB/T 22239-2019），互联网流量不得直接进入 II 区（过程监控区）。因此 OpenADR VEN 部署在**新增 DMZ 区**，通过物理隔离装置与 II 区通信。详见 §5.5 安全加固方案。

```

## 3. 电力专用通道方案详解

### 3.1 方案概述

电力专用通道方案是指通过**电力行业专有通信网络**（基于 SDH/OTN 的电力调度数据网）和**电力专用通信协议**（如 IEC 60870-5-104、IEC 61850 MMS、电力专用文件传输协议）传输 DR 信号的方案。这是目前国内电网公司（国网、南网）主流的 DR 信号下发方式。

| 项目         | 内容                                                   |
| ------------ | ------------------------------------------------------ |
| **通信网络** | 电力调度数据网（SDH/OTN 专线）                         |
| **物理隔离** | 正反向物理隔离装置（南瑞 SysKeeper / 四方 CSC 系列）   |
| **通信协议** | IEC 60870-5-104 / IEC 61850 MMS / 电力专用文件传输协议 |
| **数据格式** | CIM/XML / 电力专用报文格式                             |
| **安全机制** | 物理隔离 + 纵向加密认证 + 国密 SM2/SM3/SM4             |
| **实时性**   | 秒级（受文件摆渡延迟影响）                             |
| **部署成本** | 高（物理隔离装置 ¥10-20 万/台，专线接入费另计）        |

### 3.2 通信架构（安全加固版）

> **⚠️ 安全设计说明**：电力专用通道的通信架构保持不变，物理隔离装置部署在 II 区与 III 区之间。OpenADR 通道的 DMZ 区独立于本架构，两者在 II 区融合控制器处汇合。详见 §5.5。

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  电网公司侧（III 区 / 管理信息区）                                           │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │  电网 DR 调度系统                                                     │  │
│  │  生成 DR 指令（CIM/XML 格式）                                        │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                    │                                         │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │  反向隔离装置（电网侧 III → II）                                     │  │
│  │  文件摆渡 DR 指令到电力专网侧                                        │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
├═════════════════════════════════════════════════════════════════════════════┤
│  电力调度数据网（SDH/OTN 专线）                                             │
├═════════════════════════════════════════════════════════════════════════════┤
│  VPP 聚合商侧（II 区 / 过程监控区）                                         │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │  正向隔离装置（VPP 侧 II → III）                                     │  │
│  │  接收电网侧摆渡的 DR 指令文件                                        │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                    │                                         │

## 5. 混合部署策略（安全加固版）

### 5.1 安全设计原则

混合部署方案在附录C原始版本的基础上，进行了全面的安全加固。核心设计原则如下：

| 原则           | 说明                                                                     | 对应措施                                                    |
| -------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------- |
| **安全域隔离** | 不同安全等级的组件必须部署在对应的安全域中，互联网流量不得直接进入 II 区 | OpenADR VEN 部署在新增 DMZ 区，通过物理隔离装置与 II 区通信 |
| **最小暴露面** | DMZ 区组件最小化，仅运行必要进程                                         | DMZ 区 VEN 无数据库、无消息队列、无 Web 服务                |
| **单向数据流** | 数据流方向受物理隔离装置约束，禁止反向穿透                               | DMZ→II 区通过反向隔离装置，II→DMZ 仅限健康状态文件          |
| **默认拒绝**   | 未明确允许的通信一律禁止                                                 | 跨区通信协议矩阵严格限定                                    |
| **纵深防御**   | 单点失效不导致整体安全失效                                               | 双通道独立运行，仲裁签名机制兜底                            |

### 5.5 安全加固方案详解

#### 5.5.1 修复1：OpenADR VEN 迁出 II 区 → 部署到 DMZ 区

**问题根因**：原始方案将 OpenADR VEN 部署在 II 区（聚合层），导致互联网/VPN 流量直接进入 II 区，物理隔离被逻辑旁路。

**修复措施**：

| 维度             | 原始方案（有风险）         | 安全加固后                                                 |
| ---------------- | -------------------------- | ---------------------------------------------------------- |
| OpenADR VEN 位置 | II 区（聚合层）            | **新增 DMZ 区**（III 区和 IV 区之间）                      |
| 物理隔离         | OpenADR 流量直接进入 II 区 | DMZ→II 区必须经过**反向隔离装置文件摆渡**                  |
| 流量方向         | 双向（VEN↔VTN 可双向发起） | **单向**：DMZ→II 区（事件下发），II→DMZ 仅限健康状态文件   |
| 协议转换         | 融合层内直接 JSON/XML 转换 | DMZ 内完成 VEN 事件→CIM/XML→数字签名→文件摆渡              |
| DMZ 区组件       | 无                         | 仅运行 VEN 客户端 + 信号转换器，无数据库/消息队列/Web 服务 |

**DMZ 区服务器最低配置**：

| 配置项   | 要求                                                   |
| -------- | ------------------------------------------------------ |
| CPU      | 2 核 x86_64                                            |
| RAM      | 4 GB                                                   |
| 存储     | 64 GB SSD                                              |
| 操作系统 | Ubuntu 22.04 LTS（最小化安装）                         |
| 网络     | 双网卡：一张连接互联网/VPN，一张连接反向隔离装置       |
| 安全加固 | 禁用所有非必要端口和服务，仅开放 HTTPS 出站 + 文件写入 |

#### 5.5.2 修复2：融合层拆分为三个独立模块

原始方案中"DR 信号融合与仲裁层"是一个单体模块，攻击者攻破 VEN 后可直接横向移动到融合层。修复后拆分为三个独立模块，模块间无网络连接，只有文件传递：

```
┌──────────────────────────────────────────────────────────────────────────┐
│ 模块1：DMZ 信号转换器（DMZ 区）                                          │
│ 职责：                                                                    │
│ • 接收 VTN 事件                                                          │
│ • 转为 CIM/XML 格式                                                      │
│ • 附加 SM2 数字签名                                                      │
│ • 写入反向隔离装置摆渡目录                                                │
│ 安全约束：                                                                │
│ • 不存储任何 VPP 内部状态数据                                             │
│ • 不连接 II 区任何服务                                                    │
│ • 仅与 VTN 建立 TLS 连接                                                  │
└──────────────────────────────────────────────────────────────────────────┘
         │
         │ 反向隔离装置（硬件物理隔离）
         │ CIM/XML 文件摆渡（仅单向）
         ▼
┌──────────────────────────────────────────────────────────────────────────┐
│ 模块2：II 区融合控制器（II 区）                                           │
│ 职责：                                                                    │
│ • 读取摆渡过来的 CIM/XML 文件                                             │
│ • 验证 SM2 数字签名                                                      │
│ • 提取 DR 事件字段                                                       │
│ • 统一转换为 VPP 内部调度指令格式                                         │
│ 安全约束：                                                                │
│ • 不主动连接 DMZ 区任何服务                                               │
│ • 签名验证失败时丢弃文件并告警                                            │
└──────────────────────────────────────────────────────────────────────────┘
         │
         ▼
┌──────────────────────────────────────────────────────────────────────────┐
│ 模块3：双信号仲裁器（II 区）                                              │
│ 职责：                                                                    │
│ • 从两个源获取 DR 信号（OpenADR 摆渡文件 + 电力专网前置机）               │
│ • 校验时间戳和优先级                                                     │
│ • 电力专网信号优先级 > OpenADR 信号                                      │
│ • 一致性校验，差异时告警                                                 │
│ 安全约束：                                                                │
│ • 双通道正常时，OpenADR 信号仅用于校验（不直接驱动调度）                  │
│ • 切换决策需要仲裁签名授权                                               │
└──────────────────────────────────────────────────────────────────────────┘
```

**设计优势**：

- 三个模块之间**无网络连接**，只有文件传递
- 攻击 OpenADR VEN 后无法直接到达 II 区——需要物理穿过隔离装置
- 融合控制器本身不接触互联网，缩小攻击面
- 各模块可独立部署、独立更新、独立故障

#### 5.5.3 修复3：故障切换增加仲裁签名机制

原始方案中简单的健康检查+自动切换逻辑存在漏洞：攻击者可模拟主通道故障强制切换，或伪造健康检查响应。

**安全加固后的健康状态仲裁流程**：

```
┌──────────────────────────────────────────────────────────────────────────┐
│ 健康状态仲裁流程                                                          │
│                                                                          │
│ 步骤1：双通道各自独立健康检查                                              │
│   ├── 电力专网通道：II 区内前置机自检（无外部依赖，安全）                   │
│   │   • 设备在线状态                                                     │
│   │   • 链路连通性                                                       │
│   │   • 隔离装置状态                                                     │
│   └── OpenADR 通道：DMZ 区 VEN 自检 → 生成健康文件摆渡到 II 区            │
│       • VEN 进程运行状态                                                  │
│       • 最近 N 分钟内是否收到过 VTN 信号                                   │
│       • 文件摆渡是否正常                                                  │
│                                                                          │
│ 步骤2：仲裁模块对比两个健康状态                                            │
│   ├── 电力专网健康：所有检查项通过                                        │
│   └── OpenADR 健康：VEN 进程正常 + 最近收到信号 + 摆渡正常                 │
│                                                                          │
│ 步骤3：切换决策（需要仲裁签名授权）                                        │
│   ├── 主通道判断：电力专网通道正常 → 以此为唯一信号源                      │
│   │   OpenADR 信号仅作校验（不对其直接响应）                               │
│   ├── 电力专网故障 + OpenADR 正常 → 触发切换                              │
│   │   需要：2/3 仲裁节点达成一致 → 生成切换授权签名                        │
│   └── 双通道都故障 → 保持最后有效指令，触发紧急告警                        │
│                                                                          │
│ 步骤4：切换执行                                                          │
│   └── 只在收到仲裁授权签名后，才接受来自 DMZ 的 OpenADR 信号驱动调度       │
└──────────────────────────────────────────────────────────────────────────┘
```

**仲裁节点部署**：

| 仲裁节点 | 部署位置           | 职责                           |
| -------- | ------------------ | ------------------------------ |
| 节点 1   | II 区（主节点）    | 主仲裁决策，维护仲裁状态       |
| 节点 2   | II 区（备节点）    | 备份仲裁决策，主节点故障时接管 |
| 节点 3   | III 区（观察节点） | 独立观察，提供第三方视角       |

**关键安全设计**：

- **切换不是自动的**——需要仲裁签名授权
- 仲裁模块在 II 区内运行，不被 DMZ 影响
- 双通道正常时，OpenADR 信号**不直接驱动调度**，仅作为校验源
- 这避免了"攻击者伪造 OpenADR 信号→触发切换→注入恶意指令"的攻击链

#### 5.5.4 修复4：回传数据通道隔离

原始方案风险：同一份 VPP 状态数据可能通过两个通道回传，攻击者监听 OpenADR 通道即可获取电力专网级别的高敏感信息。

**安全加固后的回传数据流分离策略**：

```
┌──────────────────────────────────────────────────────────────────────────┐
│ 回传数据流分离策略                                                        │
│                                                                          │
│ OpenADR 回传（经 DMZ 区）：                                               │
│   II 区融合控制器                                                        │
│     → 生成简化报告文件（通过正向隔离装置摆渡到 DMZ 区）                    │
│     → DMZ 区 VEN 发送到 VTN（标准 OpenADR Report 格式）                   │
│                                                                          │
│   报告内容：仅包含                                                         │
│   • DR 事件 ID                                                           │
│   • 参与状态（optIn/optOut/active）                                      │
│   • 实际削减功率（聚合值，不含设备级细粒度数据）                           │
│                                                                          │
│ 电力专网回传（经原通道）：                                                  │
│   II 区电力专网前置机                                                     │
│     → 电网 DR 调度系统（标准 CIM/XML 格式）                               │
│                                                                          │
│   报告内容：全量执行结果                                                    │
│   • 设备级数据（每台设备的实际功率变化）                                   │
│   • SOC 状态                                                             │
│   • 电压/电流质量数据                                                     │
│   • 响应时间戳                                                           │
│                                                                          │
│ 设计原则：                                                                │
│ • OpenADR 回传只包含"参与 DR 事件"的最小必要数据                           │
│ • 电力专网回传包含完整的执行结果（合规+安全，因为物理隔离）                 │
│ • VPP 内部状态数据（设备清单、容量、SOC 详情）绝不通过 OpenADR 回传         │
└──────────────────────────────────────────────────────────────────────────┘
```

#### 5.5.5 修复5：故障切换后增加隔离期安全审查

当系统被迫切换至 OpenADR 通道时（电力专网故障），增加以下安全审查流程：

```
┌──────────────────────────────────────────────────────────────────────────┐
│ 切换后的安全审查流程                                                      │
│                                                                          │
│ 切换到 OpenADR 通道后：                                                   │
│                                                                          │
│ 1. 所有通过 OpenADR 下达的调度指令必须经过"增强校验"                       │
│    - 校验指令格式和字段边界（防止注入攻击）                                │
│    - 校验指令的功率/容量值是否在合理范围内（异常值告警）                    │
│    - 校验指令时间戳是否合理（防止重放攻击）                                │
│                                                                          │
│ 2. 执行以下操作前需要人工确认：                                            │
│    - 切换调度模式（如从正常模式切到保供模式）                              │
│    - 大幅度调整功率目标（>20% 变化）                                      │
│    - 涉及多台设备同时操作的批量指令                                       │
│                                                                          │
│ 3. 持续监控模式：                                                         │
│    - 记录所有通过 OpenADR 下达的指令日志（不可篡改存储）                    │
│    - 对比 OpenADR 指令与最近一次电力专网指令的差异                         │
│    - 差异超过阈值时触发告警                                               │
│                                                                          │
│ 4. 恢复条件：                                                             │
│    - 电力专网通道恢复后，自动切回（防抖 30 秒）                            │
│    - 切换回电力专网后，OpenADR 通道指令自动废弃                            │
│    - 生成切换事件报告，供事后审计                                         │
└──────────────────────────────────────────────────────────────────────────┘
```

## 6. 总结

**OpenADR 2.0** 和**电力专用通道**是 VPP 系统接收电网公司 DR 信号的两种互补方案，不存在绝对的优劣之分：

| 维度             | 结论                                                                                                                                                                        |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **OpenADR 2.0**  | 适合日常削峰填谷、辅助服务市场、跨省 DR、多市场参与等场景，成本低、部署快、信号模型丰富                                                                                     |
| **电力专用通道** | 适合保供电预警、等保三级合规要求等场景，安全性高、可靠性强、国内电网覆盖广                                                                                                  |
| **推荐策略**     | **安全加固混合部署**：同时部署两种通道，OpenADR VEN 部署在 DMZ 区，通过物理隔离装置与 II 区通信；日常使用 OpenADR 2.0，保供场景自动切换至电力专用通道；切换需要仲裁签名授权 |

**安全加固要点**：

1. OpenADR VEN 从 II 区迁至新增 DMZ 区，互联网流量不得直接进入 II 区
2. 融合层拆分为三个独立模块（DMZ 信号转换器、II 区融合控制器、双信号仲裁器），模块间无网络连接
3. 故障切换增加仲裁签名机制，需要 2/3 仲裁节点授权
4. 回传数据通道隔离，OpenADR 回传仅包含最小必要数据
5. 故障切换后增加隔离期安全审查

**实施路径**：

| 阶段    | OpenADR 2.0 状态             | 电力专用通道状态 | 关键任务                                                              |
| ------- | ---------------------------- | ---------------- | --------------------------------------------------------------------- |
| Phase 1 | ✅ 部署 VEN 客户端（DMZ 区） | ❌ 暂不部署      | 对接国网四川 OpenADR 试点，完成 DR 信号接收和转换原型验证；DMZ 区部署 |
| Phase 2 | ✅ 生产运行（DMZ 区）        | ✅ 部署前置机    | 部署电力专网前置机 + 物理隔离装置，实现双通道并行接收；融合层拆分     |
| Phase 3 | ✅ 生产运行（DMZ 区）        | ✅ 生产运行      | 实现仲裁签名机制 + 故障切换安全审查 + 等保三级合规认证                |
