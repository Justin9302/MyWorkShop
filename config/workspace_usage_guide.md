## 核心原则

每次接到任务，必须按以下标准流程执行，不得跳过任何步骤。

### 文档输出原则

在输出技术方案、架构设计、对比分析等文档时，遵循以下原则：

1. **代码最小化原则**：除非用户明确要求提供示例代码，否则不在文档中嵌入代码。核心算法用公式、伪代码或自然语言描述原理即可。
2. **原理优先**：用架构图、流程图、对比表、核心公式等非代码形式说明原理。如果确实需要少量代码才能说清原理，仅保留最核心的算法公式或伪代码片段。
3. **禁止行为**：不得在技术方案文档中主动添加完整的可运行代码示例、集成示例、API 调用示例等，除非用户明确要求。
4. **文件结束标记**：所有 OUTPUT 文档在写入确认结束后，末尾必须添加一行 `------END------` 作为文件结束标记，用于确认文档完整结束、未被截断。此标记之前需保留一个空行。

## 标准工作流程（5步法）

### 第一步：理解意图 + 强制上下文加载（必须，不可跳过）

接到任务后，**禁止直接开始写代码或文档**。必须先完成强制上下文加载，再问自己三个问题。

#### 强制启动序列（按顺序执行）

在理解意图之前，必须先读取以下文件：

1. `docs/model_context.md` — 项目全景、当前阶段、活跃组件版本
2. `config/active-release.yaml` — 当前发布版本、治理配置、活跃组件列表
3. `README.md` — 项目概述
4. `docs/current_workspace_creation_plan.md` — 平台治理规则
5. `constraints/baseline/context_intent_gate.yaml` — 强制前置门禁规则
6. `config/workspace_usage_guide.md` — Cline 行为标准（本文档）

> 详细加载策略请参见 `config/context-loading.yaml`
> 文档索引请参见 `docs/INDEX.md`（**按需查阅，非强制读取** — 当需要查找特定文档或确认文件用途时查阅）

#### 强制门禁执行（新增 — 不可跳过）

完成上述 6 个文件的读取后，**必须立即运行强制门禁执行器**：

```bash
python3 scripts/mandatory_gate.py
```

此脚本会验证：

1. ✅ 所有 6 个启动文件是否已被 `read_file` 读取
2. ✅ 意图确认是否已在 `<thinking>` 中完成
3. ✅ 文件完整性扫描是否已运行
4. ✅ 上下文预算是否已评估
5. ✅ 任务启动检查是否已运行

**如果脚本返回非零退出码（exit code 1），禁止继续执行任务。** 必须先完成所有未通过的检查，重新运行脚本直到通过。

**这是整个系统中最重要的规则。** 它确保所有其他规则（文件截断防护、上下文预算管理、意图确认等）都被强制执行，而不是仅仅写在文件里。

#### 理解意图三问

完成强制加载后，问自己三个问题：

```
Q1: 对方真正的需求是什么？
    - 表面需求 vs 深层需求
    - 这个任务要解决什么业务问题？

Q2: 这个任务的交付物是什么？给谁用？
    - 是内部文档还是对外输出？
    - 是技术方案还是商业决策支持？
    - 受众是谁？他们关心什么？

Q3: 如果我是对方，我看到这个交付物会怎么想？
    - 它解决了我的问题吗？
    - 它让我觉得"这就是我想要的"吗？
```

#### 意图确认输出

在 `<thinking>` 中记录：

- 用户目标、行业、地区、风险等级
- 目标输出或要修改的平台资产
- 当前 release 版本和相关组件版本
- 需要加载的工作流、约束、prompt、schema
- 缺失的信息或审批需求
- 可能编辑的文件和必须保持不动的文件
- **文件截断风险评估：列出本次任务涉及的所有待修改的已存在文件。对每个文件，先用 `wc -l` 获取行数，再用 `read_file` 读取。如果返回内容明显短于总行数（文件末尾不完整），说明被截断。根据截断状态和修改范围选择操作策略（详见下方"文件截断防护决策树"）**

---

### 第二步：行业对齐（必须，不可跳过）

在输出任何内容之前，先做行业调研：

```
1. 找对标
   - 行业头部公司的成熟方案是什么？
   - 有没有可参考的最佳实践、标准模板、成熟架构？

2. 提炼共性
   - 行业通用的能力要求、技术栈、架构模式是什么？
   - 哪些是"标配"，哪些是"差异化"？

3. 结合你的场景做差异化
   - 你的业务有什么特殊性？
   - 哪些地方需要定制，哪些可以直接复用行业标准？
```

**输出：** 在 `<thinking>` 中记录调研结果，说明参考了哪些来源。

---

### 第三步：输出初稿（目标一次对齐80%）

基于前两步的理解，输出第一版：

```
1. 结构清晰：先框架后细节，让读者一眼看到全貌
2. 内容完整：覆盖所有核心维度，不留明显空白
3. 语言精准：用词准确，避免模糊表述
4. 价值导向：不是"写了什么"，而是"解决了什么"
```

**目标：** 一次输出80分，而不是60分等反馈再改。

---

### 第四步：主动对齐确认（必须，不可跳过）

输出后，主动问：

```
1. "这个方向是否符合你的预期？"
2. "有没有需要调整的侧重点？"
3. "有没有遗漏的关键点？"
```

**目的：** 在早期发现偏差，减少无效迭代。

---

### 第五步：优化迭代

根据反馈调整，但目标是：

```
- 初稿：80分（一次对齐）
- 第一次反馈后：90分（微调）
- 第二次反馈后：95分+（打磨）
```

**禁止出现：** 60分 → 70分 → 80分 的三轮大改。

## 每次任务后的强制复盘 + 索引更新 + 头部同步

每次任务完成后，必须做三件事：

### 1. 写复盘记录

记录在 `docs/retrospective_YYYYMMDD.md`：

### 2. 检查并更新 INDEX.md

如果本次任务涉及以下任一操作，必须同步更新 `docs/INDEX.md`：

| 操作           | INDEX.md 需要更新的内容              |
| -------------- | ------------------------------------ |
| 创建新文档     | 在对应分类下添加索引条目             |
| 废弃文档       | 标记为 `[DEPRECATED]` 并说明替代文档 |
| 修改文档用途   | 更新用途描述                         |
| 修改文档优先级 | 更新优先级标记                       |
| 新增配置文件   | 在配置索引中添加条目                 |
| 新增目录       | 更新目录结构速查                     |

**判断方法：** 在复盘时问自己——"如果我现在是第一次看到这个工作空间，我能在 INDEX.md 中找到我需要的所有文档吗？"

### 3. 同步关键文件的头部简介

以下关键文件的头部包含功能描述和关联索引引用。如果本次任务修改了这些文件的内容或用途，**必须同步更新其头部简介**：

| 文件                                            | 头部包含内容                           |
| ----------------------------------------------- | -------------------------------------- |
| `config/workspace_usage_guide.md`               | 功能、启动顺序位置、关联文件引用       |
| `config/active-release.yaml`                    | 功能、启动顺序位置、关联文件引用       |
| `config/context-loading.yaml`                   | 功能、启动序列一致性声明、关联文件引用 |
| `constraints/baseline/context_intent_gate.yaml` | 功能、门禁规则概述、关联文件引用       |
| `config/session-tracking.yaml`                  | 功能、跨对话记忆系统说明、关联文件引用 |
| `docs/user_profile.md`                          | 功能、跨对话记忆系统说明、关联文件引用 |
| `docs/INDEX.md`                                 | 文档索引入口声明、最后更新日期         |

**头部简介的更新规则：**

```
1. 修改文件用途 → 更新"功能"描述
2. 修改文件关联关系 → 更新"关联"列表
3. 修改文件版本 → 更新版本号（如有）
4. 新增关键文件 → 为其添加头部简介（遵循 #===== 格式）
5. 废弃关键文件 → 在头部标记 [DEPRECATED] 并说明替代文件
```

**不遵守的后果：** 头部简介与文件实际内容不一致 → 导致 Cline 在任务启动时对文件用途产生错误理解 → 导致执行偏差。

## Git提交规则分类

工作空间中的文件分为**系统层面（System Layer）**和**工作内容（Work Content）**两大类，Git提交规则有所不同。

### 分类定义

#### 系统层面（System Layer）— 工作空间的规则与框架

这些文件定义工作空间如何运作，修改它们需要更严格的管控：

| 目录/文件              | 说明                                                     |
| ---------------------- | -------------------------------------------------------- |
| `constraints/`         | 所有约束规则（门禁、权限、安全、隐私等）                 |
| `config/`              | 所有配置文件（release、feature-flags、MCP等）            |
| `schemas/`             | 所有schema定义                                           |
| `scripts/`             | 工具脚本（不含业务脚本）                                 |
| `workflows/`           | 工作流定义                                               |
| `lattice/`             | Lattice框架代码                                          |
| `evaluators/`          | 评估器规则                                               |
| `templates/`           | 模板文件                                                 |
| `docs/` 中的规则性文档 | 如 workspace_usage_guide.md、context_intent_gate.yaml 等 |

#### 工作内容（Work Content）— 业务产出

这些是用户实际业务工作的产出：

| 目录/文件   | 说明                                 |
| ----------- | ------------------------------------ |
| `OUTPUT/`   | 输出文档（技术方案、分析报告等）     |
| `input/`    | 输入文件                             |
| `data/`     | 数据文件                             |
| `outputs/`  | 其他输出                             |
| `logs/`     | 日志                                 |
| `examples/` | 示例                                 |
| `tests/`    | 测试用例（测试框架本身属于系统层面） |

### 提交规则对比

| 维度           | 系统层面（System Layer）                                                                     | 工作内容（Work Content）                 |
| -------------- | -------------------------------------------------------------------------------------------- | ---------------------------------------- |
| **提交格式**   | 严格遵循 `type(scope): description`                                                          | 灵活格式：`type: description` 或自由描述 |
| **type 范围**  | feat, fix, chore, docs, refactor, test, style, release                                       | feat, fix, docs, chore                   |
| **scope 标识** | 必须标识系统组件：constraint, config, schema, script, workflow, lattice, eval, doc, template | 可选，建议标识业务领域                   |
| **提交频率**   | 每次修改后**必须立即提交**                                                                   | 可在任务完成后**统一批量提交**           |
| **提交前检查** | 必须通过门禁规则检查                                                                         | 建议检查，非强制                         |
| **回滚影响**   | 影响整个工作空间运作                                                                         | 仅影响特定业务产出                       |
| **push 策略**  | **必须 push 到远程服务器**                                                                   | **仅本地 commit，不 push 到远程服务器**  |

### 提交信息示例

**系统层面：**

```
feat(constraint): 新增文件截断防护三重锁定机制
fix(config): 修复MCP配置脱节 — 更新工具数量
refactor(script): 重构约束引擎加载逻辑
docs(doc): 更新workspace_usage_guide检查清单
```

**工作内容：**

```
feat: 完成VPP综合技术方案总体架构设计
docs: 更新新能源项目分析报告
fix: 修正财务模型计算错误
```

### 执行流程

```
文件修改完成
  ↓
判断文件类别
  ├── 系统层面（System Layer）
  │   ├── 提交格式：type(scope): description
  │   ├── 提交时机：立即提交
  │   ├── 提交命令：git add <文件> && git commit -m "type(scope): 描述"
  │   └── push 策略：必须 push 到远程服务器
  │       └── 命令：git push
  │
  └── 工作内容（Work Content）
      ├── 提交格式：type: description
      ├── 提交时机：任务结束时统一提交
      ├── 提交命令：git add . && git commit -m "type: 描述"
      └── push 策略：仅本地 commit，不 push 到远程服务器
```

## 文件截断防护三重锁定体系

### 问题定义

`read_file` 工具在读取大文件时可能被截断（只返回文件开头部分），但**不会告知我文件被截断了**。如果我基于不完整的内容使用 `write_to_file` 全量覆盖，会导致文件后半部分永久丢失，形成"读取截断 → 写入覆盖 → 文件变短 → 再次读取截断"的死循环。

### 核心原则

1. **新建文件不受此限制** — 新建文件时内容由我生成，不存在截断问题
2. **已存在文件必须评估** — 修改前必须确认文件完整性
3. **`replace_in_file` 是截断场景的救命工具** — 它只依赖局部匹配，不需要知道文件完整内容
4. **无法保证逻辑一致性时，必须向用户报告**
5. **自动化工具优先** — 使用 `scripts/file_integrity_check.py` 进行自动化检查，减少人工判断
6. **Git 基线校验** — 利用 Git HEAD 作为文件完整性的参考基线

---

### 第一重：检测层（Detect）— 实时发现截断

#### 强制步骤（每次修改已存在文件前必须执行）

```
步骤1: 用 wc -l <文件路径> 获取文件总行数
步骤2: 用 read_file 读取文件内容
步骤3: 运行完整性检查脚本
   python3 scripts/file_integrity_check.py check <文件路径> <read_file返回的行数>
步骤4: 根据检查结果判断
   ├── status = "ok" → 文件完整，可继续
   ├── status = "truncated" → 文件被截断，禁止 write_to_file
   └── status = "shrunk" → 文件相比 Git HEAD 缩小，需恢复
```

#### 自动化检查命令

```bash
# 检查单个文件是否被截断
python3 scripts/file_integrity_check.py check <file_path> <read_lines>

# 扫描整个目录
python3 scripts/file_integrity_check.py scan <directory>

# write_to_file 前的强制防护检查
python3 scripts/file_integrity_check.py pre-write-check <file_path> <read_lines>
```

---

### 第二重：预防层（Prevent）— 从源头避免截断

#### write_to_file 强制防护规则

| 场景                                         | 允许的操作                                 | 禁止的操作       |
| -------------------------------------------- | ------------------------------------------ | ---------------- |
| **新建文件**                                 | ✅ write_to_file                           | —                |
| **已存在文件，未截断，极小修改（改几行）**   | ✅ replace_in_file                         | ❌ write_to_file |
| **已存在文件，未截断，中等修改（改几十行）** | ✅ replace_in_file 分块修改                | ❌ write_to_file |
| **已存在文件，未截断，重大修改（几乎重写）** | ✅ write_to_file（需通过 pre-write-check） | ❌ 跳过检查      |
| **已存在文件，已截断，极小修改**             | ✅ replace_in_file 精准定位                | ❌ write_to_file |
| **已存在文件，已截断，中等修改**             | ⚠️ 向用户报告风险后决定                    | ❌ write_to_file |
| **已存在文件，已截断，重大修改**             | ❌ 告知用户无法完整读取                    | ❌ write_to_file |

#### 大文件拆分阈值

| 指标                | 阈值             | 操作                           |
| ------------------- | ---------------- | ------------------------------ |
| 文件行数            | > 2000 行        | 建议拆分为更小的模块           |
| 文件大小            | > 50 KB          | 建议拆分为更小的模块           |
| 单次 read_file 返回 | < 实际行数的 90% | 判定为截断，禁止 write_to_file |

### 第三重：恢复层（Recover）— 修复已损坏文件

#### 文件修复流程

```
发现文件已被截断/损坏
  ↓
步骤1: 从 Git HEAD 获取原始版本
   git show HEAD:<文件路径> > /tmp/<文件名>.bak
  ↓
步骤2: 对比当前版本与 Git 版本
   diff <(git show HEAD:<文件路径>) <当前文件>
  ↓
步骤3: 根据差异决定修复策略
   ├── 当前版本明显短于 Git 版本 → 从 Git 恢复
   ├── 当前版本有部分新内容 + 部分丢失 → 手动合并
   └── 当前版本与 Git 版本一致 → 文件未损坏
  ↓
步骤4: 修复后更新校验和
   python3 scripts/file_integrity_check.py update-checksums
```

#### 修复工具

```bash
# 从 Git HEAD 恢复文件
git checkout HEAD -- <文件路径>

# 对比文件差异
git diff HEAD -- <文件路径>

# 查看文件历史
git log --oneline -- <文件路径>
```

## 上下文预算管理

### 问题定义

上下文窗口（128K tokens）是有限的。每次 `read_file` 读取大文件、每次对话轮次都会消耗上下文空间。当上下文使用率超过 85% 时，`read_file` 可能返回截断内容；超过 95% 时，系统可能无法正常工作。需要主动管理上下文预算，确保关键操作有足够的上下文空间。

### 核心原则

1. **预算有限，按优先级分配** — 强制启动序列（level 1）优先于工作文件（level 2），工作文件优先于辅助参考（level 3），辅助参考优先于对话历史（level 4）
2. **每次读取前评估成本** — 大文件读取前估算 token 消耗，确认预算充足
3. **超过阈值主动释放** — 85% 释放历史，90% 释放辅助文件，95% 释放工作文件摘要
4. **向用户报告上下文压力** — 当上下文使用率超过 90% 时，告知用户当前状态和释放策略

### 优先级层级

| 层级 | 名称     | 预算       | 包含文件                                         | 释放策略          |
| ---- | -------- | ---------- | ------------------------------------------------ | ----------------- |
| 1    | critical | 40K tokens | 强制启动序列 6 个文件                            | 永不释放          |
| 2    | high     | 50K tokens | 当前任务核心工作文件                             | >95% 时生成摘要   |
| 3    | medium   | 20K tokens | INDEX.md, user_profile.md, session-tracking.yaml | >90% 时释放       |
| 4    | low      | 18K tokens | 对话历史                                         | >85% 时丢弃旧消息 |

### 操作流程

```
每次 read_file 前
  ↓
步骤1: 在 <thinking> 中记录当前上下文使用率
  ↓
步骤2: 确定目标文件的优先级层级
  ↓
步骤3: 如果文件 > 500 行，估算 token 消耗
   估算公式: lines * rate_per_line + 500(overhead)
   中文文档: 15 tokens/行
   代码: 20 tokens/行
   YAML: 12 tokens/行
   JSON: 18 tokens/行
  ↓
步骤4: 判断预算是否充足
   ├── 当前使用率 < 85% → 正常读取
   ├── 当前使用率 85-90% → 检查目标文件层级
   │   ├── level 1-2 → 正常读取
   │   └── level 3-4 → 考虑跳过或使用摘要
   ├── 当前使用率 90-95% → 触发释放策略
   │   ├── 释放 level 3 文件（保留摘要）
   │   └── 释放 level 4 文件（保留路径）
   └── 当前使用率 > 95% → 触发紧急释放
       ├── 释放 level 2 文件（生成摘要）
       └── 向用户报告上下文压力
  ↓
步骤5: read_file 后更新上下文使用率估算
```

### 强制行为

- ✅ 每次 `read_file` 前在 `<thinking>` 中记录当前上下文使用率
- ✅ 大文件（>500 行）读取前估算 token 消耗
- ✅ 超过 85% 时主动释放低优先级内容
- ✅ 超过 90% 时向用户报告上下文压力
- ✅ 使用 `replace_in_file` 替代 `write_to_file` 以减少上下文消耗（不需要重新读取完整文件）

### 禁止行为

- ❌ 在上下文使用率 > 90% 时读取 level 3-4 的大文件
- ❌ 连续多次读取大文件而不释放上下文
- ❌ 在上下文使用率 > 95% 时执行需要全局理解的重大修改
