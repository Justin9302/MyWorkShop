# Cline 工作标准（Cline Behavior Standard）

**版本：** v2.0
**生效日期：** 2026-05-11
**适用范围：** 所有任务

> **用户操作指南请参见：** `docs/workspace_usage_guide.md`
> **上下文加载策略请参见：** `config/context-loading.yaml`
> **强制前置门禁请参见：** `constraints/baseline/context_intent_gate.yaml`
> **文档索引请参见：** `docs/INDEX.md`
> **启动检查脚本请参见：** `scripts/task_init_check.py`

---

## 核心原则

每次接到任务，必须按以下标准流程执行，不得跳过任何步骤。

---

## 标准工作流程（5步法）

### 第一步：理解意图 + 强制上下文加载（必须，不可跳过）

接到任务后，**禁止直接开始写代码或文档**。必须先完成强制上下文加载，再问自己三个问题。

#### 强制启动序列（按顺序执行）

在理解意图之前，必须先读取以下文件：

1. `docs/model_context.md` — 项目全景、当前阶段、活跃组件版本
2. `config/active-release.yaml` — 当前发布版本、治理配置、活跃组件列表
3. `README.md` — 项目概述
4. `docs/current_workspace_creation_plan.md` — 平台治理规则
5. `constraints/baseline/context_intent_gate.yaml` — 强制前置门禁规则
6. `config/workspace_usage_guide.md` — Cline 行为标准（本文档）

> 详细加载策略请参见 `config/context-loading.yaml`
> 文档索引请参见 `docs/INDEX.md`（**按需查阅，非强制读取** — 当需要查找特定文档或确认文件用途时查阅）

#### 理解意图三问

完成强制加载后，问自己三个问题：

```
Q1: 对方真正的需求是什么？
    - 表面需求 vs 深层需求
    - 这个任务要解决什么业务问题？

Q2: 这个任务的交付物是什么？给谁用？
    - 是内部文档还是对外输出？
    - 是技术方案还是商业决策支持？
    - 受众是谁？他们关心什么？

Q3: 如果我是对方，我看到这个交付物会怎么想？
    - 它解决了我的问题吗？
    - 它让我觉得"这就是我想要的"吗？
```

#### 意图确认输出

在 `<thinking>` 中记录：

- 用户目标、行业、地区、风险等级
- 目标输出或要修改的平台资产
- 当前 release 版本和相关组件版本
- 需要加载的工作流、约束、prompt、schema
- 缺失的信息或审批需求
- 可能编辑的文件和必须保持不动的文件

---

### 第二步：行业对齐（必须，不可跳过）

在输出任何内容之前，先做行业调研：

```
1. 找对标
   - 行业头部公司的成熟方案是什么？
   - 有没有可参考的最佳实践、标准模板、成熟架构？

2. 提炼共性
   - 行业通用的能力要求、技术栈、架构模式是什么？
   - 哪些是"标配"，哪些是"差异化"？

3. 结合你的场景做差异化
   - 你的业务有什么特殊性？
   - 哪些地方需要定制，哪些可以直接复用行业标准？
```

**输出：** 在 `<thinking>` 中记录调研结果，说明参考了哪些来源。

---

### 第三步：输出初稿（目标一次对齐80%）

基于前两步的理解，输出第一版：

```
1. 结构清晰：先框架后细节，让读者一眼看到全貌
2. 内容完整：覆盖所有核心维度，不留明显空白
3. 语言精准：用词准确，避免模糊表述
4. 价值导向：不是"写了什么"，而是"解决了什么"
```

**目标：** 一次输出80分，而不是60分等反馈再改。

---

### 第四步：主动对齐确认（必须，不可跳过）

输出后，主动问：

```
1. "这个方向是否符合你的预期？"
2. "有没有需要调整的侧重点？"
3. "有没有遗漏的关键点？"
```

**目的：** 在早期发现偏差，减少无效迭代。

---

### 第五步：优化迭代

根据反馈调整，但目标是：

```
- 初稿：80分（一次对齐）
- 第一次反馈后：90分（微调）
- 第二次反馈后：95分+（打磨）
```

**禁止出现：** 60分 → 70分 → 80分 的三轮大改。

## 每次任务后的强制复盘 + 索引更新 + 头部同步

每次任务完成后，必须做三件事：

### 1. 写复盘记录

记录在 `docs/retrospective_YYYYMMDD.md`：

### 2. 检查并更新 INDEX.md

如果本次任务涉及以下任一操作，必须同步更新 `docs/INDEX.md`：

| 操作           | INDEX.md 需要更新的内容              |
| -------------- | ------------------------------------ |
| 创建新文档     | 在对应分类下添加索引条目             |
| 废弃文档       | 标记为 `[DEPRECATED]` 并说明替代文档 |
| 修改文档用途   | 更新用途描述                         |
| 修改文档优先级 | 更新优先级标记                       |
| 新增配置文件   | 在配置索引中添加条目                 |
| 新增目录       | 更新目录结构速查                     |

**判断方法：** 在复盘时问自己——"如果我现在是第一次看到这个工作空间，我能在 INDEX.md 中找到我需要的所有文档吗？"

### 3. 同步关键文件的头部简介

以下关键文件的头部包含功能描述和关联索引引用。如果本次任务修改了这些文件的内容或用途，**必须同步更新其头部简介**：

| 文件                                            | 头部包含内容                           |
| ----------------------------------------------- | -------------------------------------- |
| `config/workspace_usage_guide.md`               | 功能、启动顺序位置、关联文件引用       |
| `config/active-release.yaml`                    | 功能、启动顺序位置、关联文件引用       |
| `config/context-loading.yaml`                   | 功能、启动序列一致性声明、关联文件引用 |
| `constraints/baseline/context_intent_gate.yaml` | 功能、门禁规则概述、关联文件引用       |
| `config/session-tracking.yaml`                  | 功能、跨对话记忆系统说明、关联文件引用 |
| `docs/user_profile.md`                          | 功能、跨对话记忆系统说明、关联文件引用 |
| `docs/INDEX.md`                                 | 文档索引入口声明、最后更新日期         |

**头部简介的更新规则：**

```
1. 修改文件用途 → 更新"功能"描述
2. 修改文件关联关系 → 更新"关联"列表
3. 修改文件版本 → 更新版本号（如有）
4. 新增关键文件 → 为其添加头部简介（遵循 #===== 格式）
5. 废弃关键文件 → 在头部标记 [DEPRECATED] 并说明替代文件
```

**不遵守的后果：** 头部简介与文件实际内容不一致 → 导致 Cline 在任务启动时对文件用途产生错误理解 → 导致执行偏差。

## 复盘模板

```
复盘模板：

# 任务复盘 YYYY-MM-DD

## 任务：{任务名称}

## 做得好的
1. ...
2. ...

## 做得不好的
1. ...
2. ...

## 根因分析
- 为什么会出现这个问题？
- 是流程问题还是认知问题？

## 改进措施
- 下次遇到类似任务，我会怎么做？
- 需要更新工作标准吗？

## 对工作标准的建议
- 是否需要补充新的检查项？
- 是否需要调整流程？
```

## 检查清单（每次任务前过一遍）

```
□ 强制加载：已读 model_context.md、active-release.yaml、README.md、current_workspace_creation_plan.md、context_intent_gate.yaml？
□ 第一步：理解意图 — 三个问题想清楚了吗？意图确认输出写了吗？
□ 第二步：行业对齐 — 调研对标方案了吗？
□ 第三步：输出初稿 — 目标80分，结构完整吗？
□ 第四步：主动确认 — 问对方"是否符合预期"了吗？
□ 第五步：优化迭代 — 是微调还是大改？
□ 复盘：任务完成后写复盘了吗？
□ 索引更新：本次任务是否涉及新增/修改/废弃文档？INDEX.md 更新了吗？
□ 头部同步：本次任务是否修改了关键文件？头部简介同步更新了吗？
□ 会话跟踪：更新 session-tracking.yaml 和 user_profile.md 了吗？
```

---

## 进化机制

这份工作标准本身也需要持续进化：

1. **每次复盘**：检查是否有需要补充的检查项
2. **每10次任务**：做一次阶段性回顾，更新工作标准
3. **重大失误**：立即更新标准，防止同类问题再次发生
