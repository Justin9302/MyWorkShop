# 工作复盘：从"写JD"到"理解JD背后的人"

**日期：** 2026-05-11
**任务：** 基于EMS/IoT/VPP架构需求，编写IoT工程师JD

---

## 一、问题总结

### 问题1：第一反应是"写文档"，而不是"理解意图"

**我的做法：** 你一说"准备一份IoT工程师的JD"，我立刻打开编辑器开始写JD模板——岗位职责、任职要求、技术栈、面试题，一套标准模板。

**你的真实意图：** 你不是要一份模板化的JD，而是想通过JD来**筛选和吸引真正能解决你技术架构问题的人**。你的架构是NILM→IoT→EMS→VPP三级联动，你要的是一个能看懂全链路、能落地的人，不是会写STM32的人。

**教训：** 拿到任务的第一反应不应该是"开始做"，而应该是"先想清楚对方到底要什么"。JD只是载体，真正的需求是"找到对的人解决对的问题"。

### 问题2：没有主动对齐行业成熟方案

**我的做法：** 直接基于我们之前的对话内容来写JD，没有去查行业里成熟的IoT工程师JD是什么样的，没有对标主流能源IoT公司的岗位要求。

**你的期待：** 你希望我在写JD之前，先去了解行业里类似岗位（如特斯拉能源、施耐德电气、华为数字能源的IoT工程师）的JD是怎么写的，他们的能力要求是什么，薪资范围是多少，然后结合你的实际情况做适配。

**教训：** 技术方案需要对齐行业最佳实践，JD也是一样。我应该先做行业调研，再输出方案，而不是凭经验直接写。

### 问题3：输出迭代了3次才对齐，说明初始理解有偏差

**回顾整个对话：**

| 版本 | 我的输出                | 你的反馈                    | 偏差原因                       |
| ---- | ----------------------- | --------------------------- | ------------------------------ |
| v1.0 | 标准嵌入式JD，偏MCU开发 | "这只是STM32开发，外包就行" | 只看到了"嵌入式"，没看到"系统" |
| v2.0 | 加入EMS集成和云平台对接 | "35岁技术人出路是深宽管"    | 只看到了"技术栈"，没看到"人"   |
| v2.1 | 用深宽管框架重构        | 要求复盘                    | 终于对齐，但花了3轮            |

**教训：** 如果一开始就花10分钟想清楚"你到底要什么样的人"，而不是直接写，可能一次就能输出80分的版本，而不是从60分改到70分再改到80分。

## 二、应该怎么做（改进后的工作流）

### 第一步：理解意图（5分钟）

接到任务后，先问自己三个问题：

1. **对方真正的需求是什么？**
   - 表面需求："写一份JD"
   - 深层需求："找到能解决我技术架构问题的人，并且能吸引到真正有能力的候选人"

2. **这个JD要解决什么业务问题？**
   - 你的业务：NILM + IoT + EMS + VPP，三级架构，200ms实时性要求
   - 你要的人：不是写代码的，是能设计系统、理解业务、能带团队的

3. **候选人看到JD后会怎么想？**
   - 如果JD只写"精通C/C++、熟悉ESP32" → 吸引的是MCU开发工程师
   - 如果JD写"端到端系统设计、边缘-云协同、200ms实时性保障" → 吸引的是IoT技术专家

### 第二步：行业调研（10分钟）

在写之前，先做行业对齐：

1. **找对标公司的JD**
   - 特斯拉能源（Tesla Energy）的嵌入式/IoT岗位
   - 施耐德电气（Schneider Electric）的能源IoT工程师
   - 华为数字能源的嵌入式开发工程师
   - 远景能源的IoT平台工程师

2. **提炼共性要求**
   - 技术栈：C/C++、RTOS、MQTT、RS-485、Linux嵌入式
   - 系统能力：端到端架构、边缘计算、云平台对接
   - 软技能：跨团队协作、需求分析、项目管理

3. **结合你的差异化**
   - NILM事件检测（行业特色）
   - 200ms实时性（核心要求）
   - 三级架构（IoT→EMS→VPP）

### 第三步：输出初稿（15分钟）

基于意图理解和行业调研，输出第一版：

1. **岗位背景**：用你的架构图说明"我们在做什么"
2. **岗位职责**：按"深宽管"三个维度组织，而不是按技术模块
3. **任职要求**：必备条件（硬技能）+ 优先条件（加分项）
4. **面试评估**：权重分配 + 针对性面试题
5. **为什么加入**：不是画饼，而是说清楚"你能在这里获得什么"

### 第四步：对齐确认（5分钟）

输出后，主动问：

1. "这个JD的定位是否符合你的预期？"
2. "有没有需要调整的侧重点？"
3. "薪资范围和团队规模是否准确？"

### 第五步：优化迭代（按需）

根据反馈调整，但目标是**一次对齐80%**，而不是从60%开始改。

## 三、具体改进措施

| 改进点       | 之前                    | 之后                                           |
| ------------ | ----------------------- | ---------------------------------------------- |
| **任务理解** | 直接开始写              | 先问三个问题：真实需求？业务问题？候选人视角？ |
| **行业对齐** | 凭经验写                | 先调研对标公司JD，提炼共性，再差异化           |
| **输出质量** | 60分初稿，3轮迭代到80分 | 目标一次输出80分，1-2轮微调到90分              |
| **反馈利用** | 被动接受反馈再改        | 主动对齐确认，减少迭代次数                     |
| **复盘习惯** | 没有                    | 每次任务后做简短复盘，持续进化                 |

---

## 四、对你这次任务的最终理解

你现在需要的不是一个"写JD的工具"，而是一个**能理解你的技术架构、理解你的用人哲学（深宽管）、并能把这些转化为吸引人才的文案**的合作伙伴。

JD本身只是结果，真正的价值在于：

1. **帮你想清楚**：你到底需要什么样的人
2. **帮你对齐行业**：你的要求是否合理、是否有竞争力
3. **帮你吸引对的人**：让候选人看到JD就觉得"这就是我想去的地方"
